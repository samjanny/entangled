# Release engineering

This document describes the release engineering conventions for the Entangled specification repository. It is not part of the protocol specification.

## Tag naming

Tags follow these patterns:

| Type | Format | Example |
|---|---|---|
| Release candidate | v\<MAJOR\>.\<MINOR\>-rc.\<N\> | v1.0-rc.1, v1.0-rc.2 |
| Final release | v\<MAJOR\>.\<MINOR\> | v1.0, v1.1 |
| Patch release (spec text only) | v\<MAJOR\>.\<MINOR\>.\<PATCH\> | v1.0.1, v1.0.2 |

All tags use a leading "v". The release-candidate suffix uses a dot before the number ("rc.1", not "rc1") for consistency with the semver-style pre-release format.

Tag uniqueness is normative: a tag once published is immutable. To correct a mistaken tag, create a new tag with a new name; do not rewrite or move existing tags.

## Release types

### Release candidate

A release candidate marks a state in which the specification is considered substantially complete and ready for community review, but is not yet final. Multiple rc tags are expected during stabilization.

Each rc must have a corresponding entry in the repository describing what changed since the previous tag.

### Final release

A final release marks a stable specification version. After a final release, the specification text for that version is frozen except for patch releases that correct errors without changing protocol behavior (see §11 for the spec release rules).

### Patch release

A patch release corrects errors in the specification text without changing wire-format behavior, validation rules, error codes, or cryptographic primitives. Patch releases follow the rules in §11 "Spec release".

## Release process

1. Apply substantive changes via pull request review or direct commits to the main branch.
2. Verify cross-references and run any available automated checks.
3. Update this file's release notes section if applicable.
4. Tag the commit with the appropriate name from the table above.
5. Push the tag to the origin remote.
6. Verify the tag appears in the repository tag list.

Tag deletion is reserved for accidental or malformed tags only and requires explicit communication if the tag has been published or referenced externally.

The commit carrying these changes is on `main` ahead of the v1.0-rc.17 tag; rc.18 will be tagged on that commit (or a successor including any soak-period fixes) once the rc.17 soak window concludes without blockers. Date: TBD (target shortly after rc.17 soak completes)

Changes since v1.0-rc.17 (which equals rc.16 plus the Lotto 6 playbook update and the README updates committed under `docs:` after the rc.16 retag):

This rc lands a textual errata tranche identified as Lotto 7: ten low-severity clarifications aggregated into a single commit before tagging. No wire-format change; no schema change; the diagnostic catalog is unchanged. One existing diagnostic `details` field gains a precision constraint. One §10 SHOULD-level rule (cross-session migration history) is tightened to handle a previously-uncovered ping-pong direction and gains a recall-window upper bound.

**§10 Cross-session migration history — Replacement event covers the pre-Adoption current origin (N30)** — In rc.16 the `Replacement` event was recorded only when a previously adopted successor was itself superseded. This left a hole: the cross-session ping-pong vector `A → B → A → B` was detectable in only one direction, because `A` (the original starting origin, never itself a successor before the first Adoption) was never marked as "previously replaced", so a later migration announcing `A` as a successor would not trigger the recall check. The Replacement event is now recorded in two situations: (a) at every Adoption, the pre-Adoption current origin (the announcing origin) is recorded as Replacement; (b) at the existing supersession case. Both directions of the ping-pong are now covered. The Replacement record schema is preserved; only the trigger conditions are extended.

**§10 Cross-session migration history — recall window upper bound (N31)** — The recommended 30-day recall window now has an explicit SHOULD-NOT-exceed of 365 days. Clients with bounded storage MAY enforce a smaller cap, whether by time or by event count (for example, the most recent 100 migration events per publisher profile, evicting the oldest first), provided the cap remains at or above the 7-day floor. Bounds the migration-history storage per publisher profile so that a long-lived `K_publisher.pub` does not accumulate unbounded events.

**§00 v1.0 limitations — publisher history portability (N32)** — Adds an explicit limitation entry stating that Entangled v1 does not specify a serialization format or migration mechanism for publisher history (trust-state pinning records, migration history, abandonment records). A user who switches client implementations resets these records and must re-establish them through PIP-confirmed out-of-band channels. The protocol's identity guarantees still hold across the switch (the new client treats the publisher as First contact); only cross-session continuity benefits are lost. Documents an existing v1.0 design choice rather than introducing one.

**§01 Glossary — `Rendering session` (N11)** — New glossary entry defines a rendering session as the lifetime of a single client commitment to render a specific document instance: it begins after Stages 6 through 9 succeed, ends on user-initiated reload, navigation away, or replacement of the underlying manifest by a newer one. In-flight retry attempts share the same session. Disambiguates the term used in §03 (no-retry rule for image verification failure) and §10.

**§08 Canary — `summary surface` aligned to §10 chrome terminology (N12)** — The §08 phrase "the canary's summary surface" is cross-referenced to §10 "Always-visible compact indicators" so implementations do not interpret the two terms as distinct UI surfaces. The complementary "expandable detail surface" of §10 is cited as the natural location for the contents of `freshness_proof`. No normative change; cross-reference clarification only.

**§10 Abandon retained publisher identity — deletion scope (N13)** — The `delete the active trust-state record for P` step is extended to enumerate what the deletion includes: the TOFU-pinned or Externally verified state itself, the recorded set of authorized origins for the publisher profile, and any pending migration-history events naming `P`. Cached manifests for those origins are explicitly orphaned and evicted by normal cache rules; the client MUST NOT use them as current after the deletion step. Closes the rc.14 ambiguity about what a `K_publisher.pub` abandonment removes from local storage.

**§10 Migration confirmation — `affirmative confirmation` defined (N14)** — The phrase "the user's affirmative confirmation" is now defined explicitly as the user activating a dedicated chrome control whose semantics are unambiguously "accept the migration" — a button, key combination, or equivalent affordance. Passive events (focus changes, mouseover, scroll, dismissal of unrelated UI, navigation away and back, timeout-based auto-acceptance) are explicitly excluded from counting as affirmation.

**§10 Migration confirmation — `trust-state lifetime` defined (N15)** — The phrase "during the same trust-state lifetime" used in the migration re-prompting allowance is now defined: a trust-state lifetime for a publisher identity `P` begins when the client transitions `P` into a retained trust state (TOFU pinning or Externally verified) and ends on (a) user-invoked abandonment, (b) revert to First contact through Changed/mismatch resolution, or (c) user-initiated identity reset. No implicit expiration timer. Re-prompting on the same `(announcing_origin, successor_origin)` pair is now also required when the recall check defined in "Cross-session migration history" names the successor as a previously-replaced address.

**§10 Chain depth and cycle prevention — current origin after cycle rejection (N21)** — When a successor address is rejected as a chain cycle under the `visited_origins` rule, the spec now states explicitly that the publisher profile retains the most recently verified successor adopted earlier in the same flow as the current origin, and that the flow's root origin remains accessible through publisher-history controls. Future fetches addressed at any origin in `visited_origins` MAY use that origin's cached manifest if one is held and is still within its refresh policy; the cycle rejection invalidates the new migration adoption, not the prior verifications.

**§11 `E_ORIGIN_EXPIRED.details.now` — minute-precision rounding (N18)** — The `details.now` field SHOULD be rounded down to minute precision (UTC, RFC 3339 form `YYYY-MM-DDTHH:MM:00Z`). The minute-precision constraint limits the precision of any clock-skew leak when the diagnostic is logged or transmitted to third parties (crash reports, support channels) without compromising the diagnostic's usefulness for clock-skew troubleshooting, where minute-level resolution is sufficient.

**Diagnostic catalog summary.** No new error codes. One existing `details` field gains a precision constraint: `E_ORIGIN_EXPIRED.details.now` rounds down to minute precision. The rc.16 `details` schema is described as `SHOULD include`, so the precision constraint does not break any conforming rc.16 implementation that already emits second-precision values; it tightens future implementations.

**Wire format summary.** Unchanged. The wire-level `spec_version` remains `"1.0"`. No schema additions or removals on any document kind. JCS canonicalization, NFC, byte caps, and all other input restrictions are unchanged. All rc.17 documents validate identically under rc.18.

**Behavioral compatibility.** All changes are clarifications, additive extensions, or definitional tightenings of existing rules. The `Replacement` event extension (N30) changes the set of recorded events under the SHOULD-level migration-history mechanism but does not change any MUST-level requirement; rc.16 implementations that do not maintain migration history at all remain fully conformant. The recall-window upper bound (N31) is a SHOULD-NOT-exceed; rc.16 implementations that chose recall windows ≤ 365 days remain conformant by default. The §00 portability note (N32) is a limitation, not a requirement. The §10 abandon, affirmative-confirmation, trust-state-lifetime, and current-origin clarifications (N13, N14, N15, N21) define previously-undefined terms with the meaning the spec already implied; no previously valid behavior is now invalid. The `details.now` precision constraint (N18) tightens an optional `details` field; rc.16 emitters of second-precision values become non-conformant only against the SHOULD-level guidance, not the MUST-level diagnostic structure.

**Corpus.** `corpus/corpus.json` — `rc_target` bumped from `"1.0-rc.16"` to `"1.0-rc.18"` (rc.17 was content-identical to rc.16; no separate corpus snapshot is needed for rc.17). Total vectors unchanged at 34; the 34 existing vectors are byte-for-byte identical between rc.16 and rc.18 corpora since rc.18 introduces no new vectors and changes no existing diagnostic codes or schema.

### v1.0-rc.17

Date: 2026-05-11

Changes since v1.0-rc.16:

This rc adds no normative protocol changes. It bundles the post-rc.16 documentation tranches (Lotto 6 operator-playbook operationalization of W2, plus the README updates that brought the high-level docs into alignment with rc.13–rc.16 wire-format additions) into a single tagged snapshot suitable as a v1.0 release candidate. The wire format, schemas, diagnostic catalog, and corpus are byte-for-byte identical to rc.16; an implementation conforming to rc.16 conforms to rc.17 without modification.

**Lotto 6 — operationalization of W2 in the operator playbook (`docs/operator-playbook.md`)** — The first-pass audit identified W2 as a structural ALTA limitation: Entangled v1 has no in-band cryptographic revocation of `K_runtime`, so a compromised runtime key authorizes content forgery for the duration of the canary window plus the post-rotation residual. The protocol-level closure of W2 is deferred to a future major (v1.1 or v2) where a `runtime_revocation` mechanism with clock-anchor semantics can be designed cleanly. In the meantime, the playbook is extended in three places to make the residual exposure concrete and the response procedure actionable:

* §3.3 "K_runtime" — quantifies the maximum compromise window: canary interval (≤90 days per §08) plus the §10 300-second clock-skew tolerance.
* §7 "Canary and runtime rotation ceremony" — adds a new "Choosing canary interval" subsection with cadence floors per threat profile: high-threat (journalism with sensitive sources, financial services) 7 days; medium-threat 14–30 days; low-threat 30–60 days; 60–90 days discouraged because the canary stops being a meaningful security signal.
* §16 "Runtime key compromise response" — substantially expanded from a flat 8-step procedure to: a "Compromise window" subsection decomposing the exposure into three temporal phases (pre-discovery, pre-rotation, post-rotation residual) each with quantitative bounds; expanded steps that prescribe immediate-rotation cadence (`next_expected = 7 days` even on deployments normally using longer intervals); a new "Out-of-band announcement" subsection with a complete announcement template covering publisher PIP, compromised and replacement `K_runtime.pub`, compromise window in UTC, affected canary `issued_at`, reader instructions, and incident description; a new "Reader guidance" subsection with explicit safe/suspect/action/non-action items; and an expanded "Limitation" subsection listing the concrete consequences of the missing in-band revocation and pointing to the v1.1+ roadmap.

The playbook is non-normative; these changes do not affect protocol conformance. They do shift the operator's posture from "rotate when you remember" to "rotate by threat profile, with prepared offline ceremony state and PIP-confirmed out-of-band channels actively maintained".

**README updates** — The post-rc.16 README pass corrected drift accumulated during the additive rc cycle.

* `README.md` versioning section: the prior text "any change to the accepted wire format, including additive fields, is a breaking protocol change and requires a new protocol version" was contradicted by what we actually did in rc.13 (added `migration_pointer`) and rc.14 (added `origin.not_after`) without bumping `spec_version`. The text is reformulated to clarify that during the pre-release rc cycle, the closed schema MAY be extended additively with optional fields without bumping `spec_version`; documents valid under an earlier rc remain valid under a later rc. The freeze rule applies once v1.0 is tagged final.
* `README.md` "Identity continuity": adds a paragraph citing `migration_pointer` as the in-band mechanism for origin rotation, with reference to chain-depth and per-flow cycle prevention. The high-level overview now mentions the rc.13–rc.14 mechanisms explicitly.
* `corpus/README.md` vector ID category: extended from "100-199 negative" to "100-199 single-document negative diagnostics, 200-299 multi-document scenarios such as migration", to accommodate vector 200 (the migration successor-origin-expired vector added at rc.16).

### v1.0-rc.16

Date: 2026-05-11

Changes since v1.0-rc.15:

This rc lands a small follow-up tranche identified as Lotto 5: one rename for clarity, one new SHOULD-level mitigation for cross-session migration cycles, and the first corpus coverage of `origin.not_after` and `migration_pointer`. No wire-format change; no schema change; one diagnostic-catalog field is renamed (additive; rc.15 consumers see the previous name as absent).

**§11 `E_MIGRATION_MISMATCH.details.underlying_diagnostic` renamed to `underlying_diagnostic_code` (N22)** — The rc.15 field name `underlying_diagnostic` was ambiguous about scope: read literally it could be either «the diagnostic code identifier» (a string) or «the structured diagnostic record» (an object with `code`, `stage`, `details`). The intent was the former. The field is renamed to `underlying_diagnostic_code` and its definition explicitly states «code identifier only, encoded as a string; not the full structured diagnostic record». The successor's own `details` object is not nested. An operator wishing to inspect the successor's full diagnostic record fetches the successor manifest in isolation and observes the diagnostic produced by the standard pipeline. The §10 "Successor verification" prose is updated to use the new name. Rc.15 consumers reading the `details` of an rc.16 `E_MIGRATION_MISMATCH` see the rc.15 `underlying_diagnostic` key as absent and the rc.16 `underlying_diagnostic_code` key as unrecognized; the diagnostic semantics (migration rejected) are unchanged. This is a clarification rename, not a functional change; the rc.15 wire-level diagnostic schema is described as `SHOULD include`, so rc.15 implementations were never required to emit `underlying_diagnostic` in the first place.

**§10 cross-session migration history (N20)** — Adds a new SHOULD-level subsection «Cross-session migration history» under «Origin migration» that mitigates the cross-session ping-pong vector identified in the third-pass audit (an `A → B` migration in one session followed by `B → A` in the next, forced on every fresh navigation by an empty per-flow `visited_origins`). The subsection defines two new event classes recorded in publisher history per `K_publisher.pub`: **adoption** (a successor address adopted into the publisher profile) and **replacement** (a previously adopted successor superseded by a newer migration announcement). Clients that maintain migration history SHOULD consult publisher history when processing a new migration to a successor address, looking for prior replacement of that address within a recall window. The recommended recall window is 30 days; configurable, with a 7-day minimum and a discouraged-but-permitted zero (no recall). When a successor is in the recall window as a previously-replaced address, the client SHOULD raise friction: for **Externally verified** and **TOFU pinned** the existing user-confirmation requirement applies but the dialog SHOULD surface the recall information; for **First contact**, where automatic adoption of one hop is otherwise permitted, the client SHOULD instead require explicit user confirmation. The mitigation is SHOULD-level rather than MUST because v1 does not specify a publisher-history storage backend beyond what is required for trust-state continuity, and migration history introduces a new event class within publisher history. Implementations that do not maintain migration history are not non-conformant; the limit is documented as a v1.0 limitation in §00. `visited_origins` (per-flow, MUST) and migration history (per-publisher, SHOULD) are independent mitigations: the former rejects intra-flow cycles outright as `E_MIGRATION_INVALID`; the latter raises friction on cross-session cycles without rejecting them, since a publisher rotating between addresses for legitimate operational reasons must remain reachable. New §00 limitation entry «Cross-session migration cycle mitigation is opt-in»; new §01 glossary entry «Migration history».

**Corpus — first coverage of `origin.not_after` and `migration_pointer` (N23)** — The corpus generator gains support for the rc.14 `origin.not_after` and `migration_pointer` fields on `make_manifest`, the `vec()` helper gains a `diagnostic_details` parameter for structured diagnostic outcomes, and a second origin keypair (`ORIGIN_SEED_2` / `origin_pub_2`) is added for migration scenarios. Two new vectors are emitted: **006-manifest-valid-not-after** (positive) — minimal valid manifest declaring `origin.not_after = 2027-05-07T00:00:00Z`, exercising rc.14 schema acceptance and Stage 5 cross-field semantic checks per the rc.15 Stage 5 clarification; **200-migration-successor-origin-expired** (negative, migration outcome) — announcing manifest with `migration_pointer` to a successor whose own `origin.not_after` has passed at `clock_now` (2026-05-07). The successor manifest is in `extra_files/successor_manifest.json`. Expected outcome: `E_MIGRATION_MISMATCH` with `details.mismatch_field = "successor_stage9_failure"` and `details.underlying_diagnostic_code = "E_ORIGIN_EXPIRED"` — first vector exercising the rc.15 `successor_stage9_failure` path. The reject verdict on vector 200 refers to the migration adoption outcome; the announcing manifest is itself accepted at its origin, which is implied by the vector's structure. Total vectors: 34 (was 32). All previously emitted vectors are byte-for-byte unchanged.

**Diagnostic catalog summary.** No new error codes. One existing `details` field renamed: `E_MIGRATION_MISMATCH.details.underlying_diagnostic` → `underlying_diagnostic_code` (N22). The rc.15 `details` schema is described as `SHOULD include`, so the rename does not break any conforming rc.15 implementation — rc.15 emitters never depended on the field appearing under a specific name in their own output.

**Wire format summary.** Unchanged. The wire-level `spec_version` remains `"1.0"`. No schema additions or removals on any document kind. JCS canonicalization, NFC, byte caps, and all other input restrictions are unchanged. All rc.15 documents validate identically under rc.16. The new corpus vectors exercise schema constructs (`origin.not_after`, `migration_pointer`) that were already permitted at rc.14 but not previously covered by the corpus.

**Behavioral compatibility.** N22 is a clarification rename of an optional diagnostic field; no behavior change. N20 adds a SHOULD-level mitigation; clients that ignored N20 in rc.15 (which all do, since N20 is new in rc.16) remain conformant. N23 is corpus-only, no normative spec change. No previously valid behavior is now invalid.

**Deferred — partially closed.** N20 is now addressed at SHOULD level rather than fully closed. The MUST-level promotion would require v1 to prescribe a publisher-history storage backend, which is intentionally left unspecified in v1.0. A future major (v1.1 or v2) may revisit. The limit is documented in §00.

**Corpus.** `corpus/corpus.json` — `rc_target` bumped from `"1.0-rc.15"` to `"1.0-rc.16"`. Total vectors 34 (32 → 34). The 32 prior vectors are byte-for-byte identical between rc.15 and rc.16 corpora.

### v1.0-rc.15

Date: 2026-05-11

Changes since v1.0-rc.14:

This rc lands a small textual hardening tranche identified as Lotto 4: three patch-level fixes addressing internal inconsistencies and a normative gap in the rc.14 text. No wire-format change; no schema change; the diagnostic catalog is extended with two additional `details` fields on an existing error code.

**§10 Stage 5 — cross-field semantic checks (N16)** — The Stage 5 closed-schema validation list is extended with a sixth bullet acknowledging cross-field semantic checks declared by the owning section, including temporal-relation constraints between two fields. The §06 `origin.not_after` constraints (`not_after` strictly later than `canary.issued_at`; not more than 5 years after `canary.issued_at`) are explicitly cited as an instance of this category. Without this addition, the Stage 5 definition listed only per-field and nested-object/array checks, leaving a textual ambiguity about whether the two cross-field arithmetic constraints on `not_after` belonged at Stage 5 (where rc.14 assigns them under `E_ORIGIN_INVALID`) or somewhere later in the pipeline. The §10 prose at "Stage 9: path and origin binding" is also tightened to cite "Stage 5 definition above" when explaining where the `E_ORIGIN_INVALID` rejection occurs.

**§10 Clock skew tolerance — past-bound checks and broken cross-reference (N17)** — Two issues are addressed. First, a textual cross-reference at the §10 Stage 9 prose pointing to a section called "Clock and tolerance below" is corrected to "Clock skew tolerance below"; the section it intended to reference has always been titled "Clock skew tolerance". Second, the "Clock skew tolerance" section is extended with a symmetric past-bound case: the same 300-second tolerance that applies to future-bound checks (`manifest.updated`, `canary.issued_at`) now applies symmetrically to past-bound expiration checks, with `origin.not_after` (§06) as the only field in v1 to which it applies. The rejection formula is `current_time > timestamp + 300 seconds`. The user-presentation hint about local-clock incorrectness is extended to cover `E_ORIGIN_EXPIRED` as well as the previously listed diagnostics. The 300-second tolerance buys the publisher a margin to publish a successor manifest near the declared instant without producing a brief window of false-positive rejection by clients with slightly fast clocks.

**§11 `E_MIGRATION_MISMATCH` details — preserve underlying Stage 9 cause (N19)** — The `E_MIGRATION_MISMATCH` `details` schema is extended in two ways. The `mismatch_field` enumeration gains a fifth value, `successor_stage9_failure`, used when the successor manifest fails any Stage 1 through 9 check independently of the migration-binding fields (publisher pubkey, address, origin pubkey). A new optional field `underlying_diagnostic`, present only when `mismatch_field` is `successor_stage9_failure`, carries the structured diagnostic code that the successor manifest's pipeline would have reported in isolation (for example, `E_ORIGIN_EXPIRED` for a successor whose own `origin.not_after` has passed, `E_SIG_VERIFICATION` for a successor signature failure, or `E_TRUST_MISMATCH` for a successor whose retained identity already conflicts with the announced publisher key). The migration is rejected under `E_MIGRATION_MISMATCH` regardless of the underlying cause; the new field is informational only, intended to give publisher operators enough signal to distinguish "the successor address is wired to the wrong key" from "the successor manifest itself is broken" without requiring out-of-band diagnostic lookup. The `successor_publisher_pubkey` field, when included, is now scoped to cases where the successor's own Stage 5 schema validation succeeded; for earlier-stage failures it is omitted. The §10 "Origin migration" subsection prose at "Successor verification" is updated to reference the new `details.mismatch_field` and `details.underlying_diagnostic` semantics.

**Diagnostic catalog summary.** No new error codes. One existing code's `details` schema is extended additively: `E_MIGRATION_MISMATCH` gains the `successor_stage9_failure` value on `mismatch_field` and the optional `underlying_diagnostic` field. Implementations consuming the rc.14 diagnostic format remain forward-compatible: rc.14 consumers that hardcode the previous `mismatch_field` enumeration will see an unrecognized value when an rc.15 implementation reports `successor_stage9_failure`, but the diagnostic semantics (migration rejected) are unchanged.

**Wire format summary.** Unchanged. The wire-level `spec_version` remains `"1.0"`. No schema additions or removals on any document kind. JCS canonicalization, NFC, byte caps, and all other input restrictions are unchanged. All rc.14 documents validate identically under rc.15.

**Behavioral compatibility.** All rc.15 changes are clarifications and additive extensions of existing diagnostic data. No previously valid behavior is now invalid. Conforming rc.14 clients are not made non-conformant by rc.15; rc.15 clients reporting the new `details` values are not non-conformant under rc.14 because the rc.14 diagnostic schemas are described as `SHOULD include`, not `MUST include exactly`.

**Deferred.** N20 (cross-session migration cycles, forced re-migration, and the persistent migration history that would mitigate them) was identified in the third-pass audit as a MEDIA-severity finding but requires a design decision about how to record migration history persistently and how to set the recall TTL. It is not included in this rc and remains tracked for future work, possibly v1.1.

**Corpus.** `corpus/corpus.json` — `rc_target` bumped from `"1.0-rc.14"` to `"1.0-rc.15"`. Total vectors unchanged at 32; the existing vectors are unchanged byte-for-byte and validate identically under rc.15 since all rc.15 changes are textual or additive on diagnostic `details` fields, and no existing vector exercises `E_MIGRATION_MISMATCH` with a successor Stage 9 failure path.

### v1.0-rc.14

Date: 2026-05-10

Changes since v1.0-rc.13:

This rc lands the audit-driven hardening tranche identified as Lotto 3, split into two batches: tightening of `MAY`/`SHOULD` to `MUST` and clarification of underspecified resolution flows (Lotto 1, patch-level, no schema change), and additive features for origin lifetime declaration and migration chain control (Lotto 2, additive, schema and diagnostic-catalog changes).

**Lotto 1 — patch-level tightening (§02, §03, §08, §09, §10)**

- §02 Closed-schema eager-validation MUST (W16) — New normative sentence. Implementations MUST eagerly validate every top-level field of a document against the closed schema. A parser that examines only the fields it intends to use, and ignores or defers fields it does not recognize or does not currently consume, is non-conformant: schema validation is a whole-document check at Stage 5, regardless of which fields a particular execution path reads.
- §03 No retry on image verification failure (W28) — New normative subsection. After a failure at any of steps 2–9 of the image verification pipeline (transport failure, Content-Type or media-type mismatch, oversize, hash mismatch, decode failure, dimension mismatch, pixel-budget violation), the client MUST NOT re-fetch the same `src` for the same `image` block within the same document rendering session. The bound triple `(src, sha256, media_type)` is declared by the signed document; refetching cannot change the signed expectation. A user-initiated reload, or a document fetched anew under a refreshed manifest, is a new rendering session and is not blocked.
- §08 `freshness_proof` summary visibility (N4) — Strengthened the existing presence/absence signaling rule. The presence-or-absence signal MUST be visible in the canary's summary surface — the surface that exposes the canary state without requiring expansion of a detail view, drawer, or other collapsed UI. A client that hides the presence signal exclusively behind a collapsed detail surface is non-conformant. The contents of `freshness_proof` itself, when present, MAY remain in the expandable detail surface; only the presence-or-absence indicator is required in the summary.
- §08 Canary-conflict resolution control (N2) — Strengthened the existing canary-conflict warning rules. The client MUST present an explicit user-accessible resolution control as part of the chrome warning, offering at least two distinct actions: "Keep the retained identity" (acknowledges the conflict, clears the always-visible warning, records the event in publisher history) and "Abandon the retained publisher identity" (defined in §10). Passive events MUST NOT clear the warning. The prior text required offering "the option to abandon" but did not prescribe that the offer take the form of a user-accessible UI control; clients that surfaced the warning without a usable resolution affordance left the user in a permanently bloccato state.
- §09 No `Range`/`If-Range` request headers; no `206 Partial Content` (W26) — Added `Range` and `If-Range` to the prohibited request-header list for both `GET` and `POST` requests, with a normative paragraph explaining the rationale (an Entangled document is signed as a whole and is verified, hashed for the byte cap, and digested for image binding against its complete byte sequence; partial-content fetches deliver bytes that do not correspond to any signed object). Publishers MUST treat any request carrying `Range`/`If-Range` as malformed; publishers MUST NOT emit `206 Partial Content`. The general "unlisted `2xx`" rule already covered `206` on the client side, but the previous text did not name it explicitly and did not forbid the client from issuing `Range` requests.
- §10 Abandoning a retained publisher identity (N1) — New normative subsection specifying the semantics of the "abandon retained publisher identity" action offered by the canary-conflict resolution control (§08), the Changed/mismatch resolution flow, and any equivalent high-threat-mode UI. The action MUST: delete the active trust-state record for `K_publisher.pub = P`; record the abandonment in publisher history as a terminal event including reason class; dissociate any authorized origins (including successor origins adopted under the publisher profile via `migration_pointer`); and refuse to use retained `K_runtime` authorization-history entries for verifying any new content fetched after the abandonment as if it were current publication. After abandonment, a subsequent navigation to any origin presenting `publisher_pubkey == P` is treated as First contact; the client MUST surface that an abandonment record exists at the First-contact prompt. The new subsection also distinguishes "abandon the site" (Changed/mismatch resolution; preserves the retained identity record) from "abandon retained publisher identity" (severs the trust relationship); the two are distinct user actions and MUST be presented in chrome as distinct choices.
- §10 Migration confirmation for retained identities (N5) — Strengthened the prior `SHOULD` on user confirmation before automatic navigation to a successor origin. The strength now depends on the announcing publisher's trust state: for **Externally verified** or **TOFU pinned** identities, the client MUST obtain the user's affirmative confirmation before navigating to the successor origin and before migrating any cached state; for **First contact**, the prior `SHOULD` is retained. The confirmation dialog MUST present both addresses, the complete 24-word PIP, and the `migration_pointer.announced_at` timestamp, with no destructive default. A client that has obtained confirmation for a specific `(announcing, successor)` pair MAY proceed without re-prompting for the same pair within the same trust-state lifetime. Background auto-fetch of the successor manifest for verification purposes remains permitted, provided publisher-controlled content from the successor is not rendered before user confirmation.

**Lotto 2 — additive (§05, §06, §10, §11, §00, §01)**

- §06 `origin.not_after` (W1) — New OPTIONAL field on the manifest's `origin` object. Declares the UTC instant after which the publisher commits that this carrier endpoint is no longer authoritative for the site under `K_publisher`. Encoded in the same RFC 3339 UTC form as `updated` (`YYYY-MM-DDTHH:MM:SSZ`). Constraints: MUST be strictly later than `canary.issued_at`; SHOULD be strictly later than `canary.next_expected`; MUST NOT be more than 5 years after `canary.issued_at`. A manifest with `origin.not_after` violating these constraints is rejected at Stage 5 as `E_ORIGIN_INVALID`. A manifest whose `origin.not_after` is at or before the client's clock (within the §10 clock-skew tolerance) is rejected at Stage 9 as `E_ORIGIN_EXPIRED`; anti-downgrade still applies, and a newer manifest for the same `K_publisher.pub` supersedes the expired one. Absent in the manifest when no expiration is declared (per §04 no-`null` discipline). Bounds the time window during which an attacker holding a compromised `K_origin_priv` can serve cached clients of an abandoned origin.
- §05 `K_origin` compromise summary — Extended the recovery paragraph to acknowledge `origin.not_after` as the optional mechanism that bounds the post-compromise serving window for cached clients; recovery remains in-band only insofar as the cached client observes the new manifest or its `migration_pointer` before `not_after` is reached.
- §10 Origin migration chain depth and cycle prevention (N6) — New normative subsection. A client supporting publisher profiles MUST enforce both an automatic chain-depth limit (at most one `migration_pointer` hop adopted without re-prompting under "User confirmation"; further hops require a new confirmation, evaluated under the trust state of the publisher identity at the intermediate origin) and a per-flow visited-origin set (`visited_origins`, initialized with the announcing origin; a successor address already in `visited_origins` is rejected as `E_MIGRATION_INVALID` with `details.reason = "chain_cycle"`). The `visited_origins` set is per-navigation and per-publisher-profile, reset when the migration-resolution flow ends, and not persisted across sessions. The chain-depth limit applies to automatic hops only; user-confirmed hops reset the counter. High-threat mode MAY set the automatic limit to zero. When the limit is reached without user confirmation, the deeper successor is treated as "pending user action": chrome displays the announcement, but the client MUST NOT auto-navigate, fetch publisher-controlled content from the deeper successor, or migrate cached state to it.
- §10 Stage 9 — Updated the Stage 9 pipeline-summary listing to include the `origin.not_after` check and the `migration_pointer` successor/chain-depth check. Updated the Stage 9 detail prose to specify that `origin.not_after` is evaluated after carrier origin binding succeeds and that the comparison uses the §10 clock-skew tolerance. Cross-references between §06, §10, and §11 are kept consistent.
- §11 — Added `E_ORIGIN_EXPIRED` (Stage 9, manifest, error) and `E_ORIGIN_INVALID` (Stage 9, manifest, error) to the Binding diagnostics catalog. `E_ORIGIN_EXPIRED` SHOULD include in `details` the declared `not_after` and the client's `now` value used for the comparison. `E_ORIGIN_INVALID` SHOULD include `reason` (`not_after_not_after_issued_at` or `not_after_beyond_5y`), the declared `not_after`, and `canary.issued_at`. Extended the existing `E_MIGRATION_INVALID` row to note that the chain-depth/cycle case also reports under this code.
- §00 — Added a new v1.0 limitation entry, "No in-band revocation of `K_origin`", noting that `origin.not_after` is the optional protocol-level bound on post-compromise serving window and that, when omitted, the recovery window is unbounded for cached clients that never observe the new manifest or `migration_pointer`.
- §01 — Added "Origin not-after" glossary entry; updated "Origin" entry to list `not_after` among origin fields; updated "Migration pointer" entry to note the chain-depth limit and visited-origin cycle check.

**Diagnostic catalog summary.** Two new error codes: `E_ORIGIN_EXPIRED`, `E_ORIGIN_INVALID`. One existing code's row text extended: `E_MIGRATION_INVALID` (chain cycle / depth-exceeded case is reported under it). No existing code is renamed or has its underlying semantics changed. Implementations consuming the rc.13 catalog need to add the two new codes; existing codes are otherwise unchanged.

**Wire format summary.** The wire-level `spec_version` remains `"1.0"`. The closed-schema field set for the manifest's `origin` object gains one optional field (`not_after`); the manifest's top-level field set and all other document kinds are unchanged. JCS canonicalization is unchanged. NFC and other input restrictions are unchanged. Manifests omitting `origin.not_after` validate identically under rc.13 and rc.14. A manifest carrying a present `origin.not_after` is rejected by rc.13 clients (which see it as an unknown nested field and fail closed-schema discipline) and accepted by rc.14 clients subject to the new semantic constraints.

**Behavioral compatibility.** All Lotto 1 changes are tightenings: documents and behaviors valid under rc.13 remain valid under rc.14, provided implementations were not silently relying on the loose `MAY`/`SHOULD` forms now tightened. The clarified resolution-control and abandonment-semantics rules formalize behavior the prior text implied but did not enforce; conforming rc.13 clients that honored the spirit of the prior text are unaffected.

**Lotto 1 — patch-level tightening (§10, §08, §01)**

- §10 First contact → TOFU pinned (W18) — Strengthened to `MUST` an explicit affirmative pinning prompt. Truncated, prefix-only, suffix-only, or "first-N + last-M" displays are not conformant. - §08 Equal `issued_at` conflict (W7) — Reframed `E_CANARY_CONFLICT` as a fault condition on the publisher identity, not a recoverable transient error. The client MUST NOT pick a deterministic "winner" between conflicting manifests by lexicographic comparison, payload size, `runtime_pubkey` value, or any other tiebreaker over manifest content; a deterministic tiebreaker is gameable by an attacker holding `K_publisher_priv` and would mask the underlying fault. The retained pre-conflict manifest stays in place for current rendering and anti-downgrade; the conflict is surfaced as a prominent chrome warning analogous to Changed/mismatch, with an option to abandon the retained publisher identity. The warning persists until the user explicitly resolves it.
- §01 — Publisher profile glossary entry now notes the conditional `MUST` for stateful clients.

**Lotto 2 — additive (§06, §10, §11, §04, §08, §02, §00, §01, corpus)**

- §06 `migration_pointer` (W22) — New optional top-level manifest field. The publisher's signed announcement of a successor carrier endpoint operated under the same `K_publisher`. Absent when no migration is announced; per §04 no-`null` discipline, encoded by omitting the field rather than by a `null` value.
- §10 Origin migration handling — New subsection. A client supporting publisher profiles MUST detect a present `migration_pointer`, display a chrome migration notice, fetch the successor manifest from `successor_origin.address`, apply Stages 1–9, and verify that `successor_manifest.publisher_pubkey` byte-equals the announcing manifest's `publisher_pubkey`. On match, the successor origin is adopted into the publisher profile. On mismatch, the announcement is rejected as `E_MIGRATION_MISMATCH`. The client SHOULD obtain user confirmation before automatic migration; a strict-mode client MAY refuse in-band migration and require out-of-band navigation, but MUST display in chrome that an announcement was present.
- §11 — Added `E_MIGRATION_MISMATCH` and `E_MIGRATION_INVALID` to the Binding diagnostics (Stage 9) catalog. `E_MIGRATION_MISMATCH` SHOULD include in `details` the announced successor address, the successor and announcing publisher keys, and the specific mismatch field. `E_MIGRATION_INVALID` covers structural well-formed but semantically invalid announcements (successor equals announcing, `announced_at` after `updated`, carrier mismatch).
- §04 Unicode normalization for user-visible strings (W6) — New normative subsection. JSON string fields whose values the client renders to the user as text MUST be encoded in NFC (Unicode Standard Annex #15). Non-exhaustive list: `canary.statement`, `meta.title`, manifest `navigation` `label`, `state_policy` `purpose`, and every block text content span and string field rendered to the user including `link.label`, `image.alt`, `code_block.content`, `feedback.statement`, `note.statement`, `submit_form` labels and option labels. NFD, NFKC, NFKD are not permitted forms. Non-NFC values rejected with `E_SCHEMA_FIELD_SYNTAX` at schema validation, before signature verification. Implementations MUST NOT silently re-normalize: re-normalization would alter the JCS canonical bytes and break the publisher's signature.
- §02 Closed-schema discipline — Made the optional-fields semantics explicit: a field is optional only if its owning section designates it optional; only fields explicitly listed (required or optional) may appear at the top level; absent values are encoded by omitting the field, never by `null`. Required for `migration_pointer` to land cleanly in the closed schema.
- §08 `freshness_proof` signaling and strict policy (W4) — Added "Client signaling on absence": the chrome MUST signal whether the current canary includes a `freshness_proof`; absence MUST NOT be silently treated as equivalent to presence. Strict policy is client-side configuration, not a manifest declaration.
- §00 — Replaced "No in-band origin migration discovery" entry with "In-band origin migration is publisher-initiated only", reflecting `migration_pointer`. Pre-existing publisher cache without a prior announcement still requires out-of-band recovery.
- §01 — Added "Migration pointer" glossary entry; updated "Manifest" entry to list `migration_pointer` among manifest fields.
- corpus — Added 4 new vectors:

Corpus vectors exercising the affected within-array uniqueness rules and the multi-key historical trial anomaly should be updated to assert the new codes; that corpus update is out of scope for this rc and will be tracked in a follow-up tranche.

The wire format, signature inputs, and signature input construction are unchanged. The wire-level `spec_version` remains `"1.0"`.

### v1.0-rc.6

Date: 2026-05-08

Changes since v1.0-rc.5:

- §02 — Reserved `/manifest.json` at the protocol level. The path is now explicitly forbidden as a content document `path`, transaction `in_response_to`, image `src` (§03), submit endpoint, and inline-link target. Added a bullet to each path-syntax restatement.
- §02 — Clarified the scope of the `request_id` / `request_hash` binding: they bind the signed transaction response to the submit body the client sent, but are not a general anti-replay mechanism against a malicious or compromised publisher backend, which may still receive, store, or reuse submit bodies and sign transaction responses for any submit body it accepts.
- §03 — Replaced the abstract image-resource verification list with a precise, ten-step ordered sequence that names the specific diagnostic for each step (`W_IMAGE_FETCH_FAILED`, `W_IMAGE_CONTENT_TYPE`, `W_IMAGE_OVERSIZE`, `W_IMAGE_HASH_MISMATCH`, `W_IMAGE_DECODE_FAILED`, `W_IMAGE_DIMENSIONS`, `W_IMAGE_BUDGET`). Made explicit that the declared `media_type` is authoritative for decoder selection while the response `Content-Type` is checked separately for header consistency.
- §03 — Added a normative WebP animation detection requirement. A client MUST determine animation status before rendering, by inspecting the RIFF chunk structure or by querying its decoding library. An implementation whose WebP library cannot expose this property reliably MUST reject all WebP resources or disable WebP support. Silently rendering only the first frame of an animated WebP is non-conformant.
- §08 — Refined the equal-`issued_at`-not-a-conflict criterion to depend solely on the JCS-canonical signed payload rather than on byte-for-byte wire equivalence and signature equality. Under deterministic Ed25519 (RFC 8032) signing the same payload under the same key produces an identical `sig`, so the canonical-payload criterion subsumes the signature criterion; framing it as canonical payload makes the protocol-level invariant clear.
- §10 — Added a "Verification key trial order" section for historical content. The order in which retained `K_runtime.pub` entries are tried is implementation-defined (reverse chronological by first-observed `issued_at` recommended). Verification under more than one distinct retained key for the same document is treated as a cryptographic anomaly, an implementation bug, or authorization-history corruption; the client MUST reject the document. No new normative error code; clients SHOULD log the condition.

This rc clarifies path reservation, image verification ordering, and historical-content trial order, and scopes the submit-binding guarantees against backend replay. None of these changes alter the wire format, signature inputs, signature input construction, or the diagnostic code catalog.

### v1.0-rc.5

Date: 2026-05-08

Changes since v1.0-rc.4:

- §04 — Added an explicit ABNF integer grammar (`integer = "0" / non-zero-digit *digit`) and a parser-level enforcement rule. Numeric tokens MUST be validated lexically before any conversion to a numeric type. JSON parsers that convert numeric tokens to IEEE 754 binary64 first are non-conforming for Entangled use because they cannot reliably distinguish `42` from `42.0` or `1e0`, lose precision above `2^53` (so `9007199254740993` becomes `9007199254740992`), and conflate `-0` with `+0`. Implementations MUST use a parser that either exposes raw numeric tokens for lexical inspection, or rejects non-integer tokens at parse time, or perform a separate raw-bytes validation pass. The integer's decimal value MUST be in `[0, 2^63 − 1]`.
- §04 — Added a "Strict base64url decoding" section that pins decoder behavior for every base64url-encoded field in the protocol (`sig`, `publisher_pubkey`, `origin_pubkey`, `runtime_pubkey`, `expected_publisher_pubkey`, `request_id`, `image.sha256`, `transaction.request_hash`). The decoder MUST use only the URL-safe alphabet (`A-Z`, `a-z`, `0-9`, `-`, `_`), reject every character outside it including `+`, `/`, whitespace, line breaks, and non-ASCII characters, reject the padding character `=`, enforce the field-declared exact ASCII length, and reject non-canonical trailing-group encodings (the unused bits in the final encoded character MUST be zero). Permissive decoders that accept padded input, ignore whitespace, accept the standard `+`/`/` alphabet, or accept non-canonical trailing-group encodings are non-conforming.

This rc tightens parsing strictness without changing the wire format, signature inputs, signature input construction, or the diagnostic code catalog. Documents that an rc.4 client accepted by virtue of a permissive JSON parser or base64 decoder may be rejected by an rc.5 client; conforming current parsers and decoders are unaffected.

The wire-level `spec_version` remains `"1.0"`.

### v1.0-rc.4

Date: 2026-05-08

Changes since v1.0-rc.3:

- §02 — Clarified that `request_hash` is computed over the JCS-canonical bytes of the parsed submit body, not over the wire bytes received. The formula already pinned this; the prose previously read "the exact submit body bytes received, after JCS-canonicalization", which was ambiguous. Insignificant whitespace and member ordering in the wire submit body are now stated explicitly to not affect the hash.
- §05 — Added an "Ed25519 verification profile" section that pins the strict, cofactorless validation rules. Public keys MUST be in canonical encoding and MUST NOT be small-order; signatures MUST use canonical `R` and canonical `S` (`0 ≤ S < L`); verification uses the cofactorless equation `[S]B = R + [k]A`. The profile aligns with `verify_strict` in `ed25519-dalek`. Implementations MUST NOT use cofactored verification or accept non-canonical encodings. This eliminates cross-implementation divergence in signature acceptance, in particular between libraries that historically split between RFC 8032 permissive and ZIP-215-style strict modes.
- §07 — Replaced the "opaque byte strings" terminology for state values with "opaque UTF-8 strings", aligning the safe-display subsection with the value field schema (`value` is a UTF-8 string). Editorial only; no wire-format change.
- §09 — Added a "Content-Encoding and Transfer-Encoding" section that forbids both headers in both directions. Publishers MUST NOT use `Content-Encoding` on any Entangled response or `Transfer-Encoding` (including `chunked`) on any response; clients MUST disable automatic HTTP-layer decompression and reject responses carrying either header. The same rules apply to submit `POST` request bodies. Closes the interop ambiguity that arose when transport stacks decompressed responses by default, which would change the byte sequence used for the byte cap (§02, §06, §10), for `Content-Length` consistency checks, and for the SHA-256 digest of image resources (§03). Adds a normative implementation note that conforming clients must use an HTTP stack whose default header injection and decompression can be disabled.
- §11 — Added `E_TRANSPORT_CONTENT_ENCODING` and `E_TRANSPORT_TRANSFER_ENCODING` to the Stage 1 transport diagnostics catalog.

This rc tightens transport and signature-verification behavior. Responses or signatures that an rc.3 client might have accepted under HTTP-stack default decompression or under cofactored Ed25519 verification can now be rejected; conforming current signers and HTTP stacks are unaffected. The wire-level `spec_version` remains `"1.0"`; the rc number tracks pre-release stabilization, not protocol identity (§11).
