# Release engineering

This document describes the release engineering conventions for the Entangled specification repository. It is not part of the protocol specification.

## Tag naming

Tags follow these patterns:

| Type | Format | Example |
|---|---|---|
| Release candidate | v\<MAJOR\>.\<MINOR\>-rc.\<N\> | v1.0-rc.1, v1.0-rc.2 |
| Final release | v\<MAJOR\>.\<MINOR\> | v1.0, v1.1 |
| Patch release (spec text only) | v\<MAJOR\>.\<MINOR\>.\<PATCH\> | v1.0.1, v1.0.2 |

All tags use a leading "v". The release-candidate suffix uses a dot before the number ("rc.1", not "rc1") for consistency with the semver-style pre-release format.

Tag uniqueness is normative: a tag once published is immutable. To correct a mistaken tag, create a new tag with a new name; do not rewrite or move existing tags.

## Release types

### Release candidate

A release candidate marks a state in which the specification is considered substantially complete and ready for community review, but is not yet final. Multiple rc tags are expected during stabilization.

Each rc must have a corresponding entry in the repository describing what changed since the previous tag.

### Final release

A final release marks a stable specification version. After a final release, the specification text for that version is frozen except for patch releases that correct errors without changing protocol behavior (see §11 for the spec release rules).

### Patch release

A patch release corrects errors in the specification text without changing wire-format behavior, validation rules, error codes, or cryptographic primitives. Patch releases follow the rules in §11 "Spec release".

## Release process

1. Apply substantive changes via pull request review or direct commits to the main branch.
2. Verify cross-references and run any available automated checks.
3. Update this file's release notes section if applicable.
4. Tag the commit with the appropriate name from the table above.
5. Push the tag to the origin remote.
6. Verify the tag appears in the repository tag list.

Tag deletion is reserved for accidental or malformed tags only and requires explicit communication if the tag has been published or referenced externally.

### v1.0-rc.31

Date: 2026-05-29

**Lotto 31 - empty-array and nested-link diagnostic codes (AMB-13, AMB-14)**

Closes issues #14 (AMB-13) and #15 (AMB-14). Pins the diagnostic code for two Stage 5 schema rejections the catalog did not clearly cover. No wire-format, schema, signature-input, or new-code change; `spec_version` remains `"1.0"`. Each amends an existing §11 catalog row's description and adds a corpus vector; no codes are added or removed.

**AMB-13 / #14: empty mandatory array.** Several arrays MUST contain at least one element (content `blocks`, `list.items`, `submit_form.fields`, `select.options`, inline content). An empty-but-present array is *under* the minimum, which neither `E_SCHEMA_FIELD_LENGTH` ("exceeds its specific length limit", over a maximum) nor the prior `E_SCHEMA_REQUIRED_FIELD` ("a required field is absent", a present array is not absent) cleanly covered. Pinned to `E_SCHEMA_REQUIRED_FIELD`: the required (first) element is absent, one code across all mandatory arrays. The §11 `E_SCHEMA_REQUIRED_FIELD` row description is amended to read "A required field is absent, or a mandatory array does not contain the minimum number of required elements (...)".

**AMB-14 / #15: nested inline link.** §03:654 and §03:703 forbid an inline `link` element inside a `link.label` or `submit_form.label`. The violation is an element of an enumerated kind appearing where that kind is not permitted (a permission rule), so it is pinned to `E_SCHEMA_BLOCK_NOT_PERMITTED`, not `E_SCHEMA_ENUM_VIOLATION` (which covers a value outside a closed value set, e.g. `carrier`, `mode`, `feedback.variant`). The §11 `E_SCHEMA_BLOCK_NOT_PERMITTED` row description is amended to "A block or inline element of an enumerated kind appears in a position that does not permit that kind. For example, a `submit_form` block in a `transaction` document, or an inline `link` element inside a `link.label` or `submit_form.label` (...)".

**Corpus.** Two new negative vectors, both signed correctly so the schema violation is the only live Stage 5 violation: `146-schema-empty-array` (content `blocks: []` -> `E_SCHEMA_REQUIRED_FIELD`) and `147-schema-nested-link` (a `link` block whose `label` contains an inline `link` element -> `E_SCHEMA_BLOCK_NOT_PERMITTED`). No existing vector input bytes change; the count moves 65 -> 67; `corpus.json` `rc_target` moves `1.0-rc.30` -> `1.0-rc.31`.

**Behavioral compatibility.** Both rejections were already required (the documents are malformed); this rc pins which Stage 5 code reports them. The Rust reference implementation already emits both pinned codes; the Java reference implementation emits `E_SCHEMA_FIELD_LENGTH`/`_SYNTAX` (empty array) and `E_SCHEMA_ENUM_VIOLATION` (nested link) and is corrected in lockstep (entangled-api-java).

**Wire format summary.** Unchanged. `spec_version` remains `"1.0"`. Two existing diagnostic-catalog row descriptions are broadened; no schema, signature-input, or code-set change.

### v1.0-rc.30

Date: 2026-05-29

**Lotto 30 - 100 KiB string cap counted in UTF-8 wire bytes (AMB-15)**

Closes issue #16 (AMB-15). Pins the counting unit of the Stage 3 per-string 100 KiB parse cap, which the spec stated as "100 KiB" without naming a unit. No wire-format, schema, signature-input, diagnostic-catalog, or behavior change for conforming documents under the cap; `spec_version` remains `"1.0"`. The pin removes a verdict divergence at the boundary between two conforming implementations.

A string near the 100 KiB cap that contains multi-byte or non-BMP characters is counted differently by a UTF-8-byte counter and a UTF-16-code-unit counter (a non-BMP code point is 4 UTF-8 bytes but 2 UTF-16 code units). One implementation rejected at the byte count, another accepted at the code-unit count, for identical wire bytes. The spec is pinned to **UTF-8 wire bytes**: "KiB" is a byte unit, the canonical document encoding is UTF-8 (section 04), and counting UTF-16 code units is a language-VM-internal artifact that would make the cap depend on the implementation language.

**Spec edits.** The unit is made explicit at all three places the cap appears: section 02 ("individual string fields MUST NOT exceed 100 KiB ... The 100 KiB count is in UTF-8-encoded wire bytes ..., not in UTF-16 code units or Unicode code points"), the section 10 Stage 3 parser-limit list, and the section 10 Stage 3 limits table.

**Corpus.** New negative vector `116-parse-string-length-utf8-unit`: a `code_block` content of 30000 U+1F600 code points = 120000 UTF-8 wire bytes (over the 102400 cap) but 60000 UTF-16 code units (under it). Verdict `reject`, diagnostic `E_PARSE_STRING_LENGTH`. An implementation counting UTF-8 bytes rejects it; one counting UTF-16 code units would wrongly accept, so the vector pins the unit. The body stays under the 1 MiB Stage 2 cap so Stage 3 fires; U+1F600 is not a control character and is already NFC, so no earlier check pre-empts the parse cap. No existing vector input bytes change; the count moves 64 -> 65; `corpus.json` `rc_target` moves `1.0-rc.29` -> `1.0-rc.30`.

**Behavioral compatibility.** No accept/reject change for any document whose strings are within the cap under either counting; only the boundary case (a near-cap string with multi-byte/non-BMP characters) is now pinned. A conforming implementation counts UTF-8 wire bytes. The Rust reference implementation already counts UTF-8 bytes (`s.len()` on the parsed string); the Java reference implementation counts UTF-16 code units and is corrected in lockstep (entangled-api-java).

**Wire format summary.** Unchanged. `spec_version` remains `"1.0"`. One parse-limit unit is made explicit; no diagnostic-catalog, schema, or signature-input change.

### v1.0-rc.29

Date: 2026-05-29

**Lotto 29 - Expired-canary precedence: Stage 10 render-block, not Stage 8 halt (AMB-12)**

Closes issue #13 (AMB-12). Pins where the Expired canary determination sits in the first-failing-stage error-precedence model: it is a Stage 10 render-block, not a Stage 8 pipeline rejection. No wire-format, schema, signature-input, JCS, NFC, byte-cap, diagnostic-catalog, or vector-input change; `spec_version` remains `"1.0"`. This aligns the section 10 prose with the existing corpus and the reference implementation; no implementation change.

Section 10 "Error precedence" is strict (the first stage that fails determines the reported diagnostic; later stages are not executed), and section 10 said Stage 8 "produces one of the five canary states", of which Expired is one. It did not say whether the Expired determination *halts* the pipeline at Stage 8. Two readings followed: (A) Expired is a Stage 8 pipeline failure reporting `E_CANARY_EXPIRED`, halting before Stage 9; (B) Expired is not a pipeline rejection but a Stage 10 render-block, so the pipeline runs through Stage 9 and a co-occurring earlier failure (for example a Stage 9 `E_ORIGIN_EXPIRED`) is reported first. On a manifest that is simultaneously canary-Expired and origin-expired the two readings report different diagnostics at different stages for identical wire bytes. This is distinct from AMB-09 (rc.23), which fixed only the *severity* of `E_CANARY_EXPIRED` and left the section 08:183 behavior unchanged; it did not address precedence or pipeline placement.

**Reading (B) is pinned.** Three reasons, in order of weight:

1. The corpus already encodes it. Migration vector `200-migration-successor-origin-expired` carries a successor that is both canary-Expired (`next_expected` 2026-05-01, past `clock_now`) and origin-expired (`origin.not_after` 2026-05-01), and its expected `underlying_diagnostic_code` is `E_ORIGIN_EXPIRED` (Stage 9). That code is reachable only if the Expired determination at Stage 8 does not halt the pipeline. Under reading (A) the vector would be unsatisfiable.
2. The section 08:185 per-session user-override distinguishes a render-block from a pipeline rejection: a render-block is user-overridable; a Stage 8 pipeline rejection (such as `E_CANARY_INVALID`, which has no override) is not. Treating Expired as a Stage 8 halt would contradict the override semantics.
3. It keeps the Stage 8 / Stage 9 separation that AMB-05 established, rather than re-mixing the two layers.

**Section 10 edits.** The Stage 8 pipeline-diagram entry and the Stage 8 prose now state that Stage 8 halts the pipeline only on a canary *rejection* (`E_CANARY_INVALID`, `E_CANARY_DOWNGRADE`, `E_CANARY_CONFLICT`, `E_CANARY_RUNTIME_REUSE`), and that the Expired state is computed, carried forward, and applied as the section 08:183 render-block at Stage 10, so the pipeline continues through Stage 9 and an earlier or Stage 9 failure is reported first under error precedence. The Stage 10 prose now states that the Expired render-block (with the section 08:185 override) is applied there, distinct from a pipeline rejection because the document reached Stage 10 and the block is user-overridable.

**Corpus.** No vector input bytes change and no vector is added: vector 200 already encoded reading (B), and the change is section 10 prose. `corpus/README.md` is corrected, where it previously described reading (A): the "Stage 9 origin lifecycle" coverage note no longer says the Expired state "stops the pipeline before Stage 9", and a note records that the `E_CANARY_EXPIRED` runtime emission point is a Stage 10 render-block (needing the render-state schema extension to exercise directly, not a `reject` vector). `corpus.json` `rc_target` moves `1.0-rc.28` -> `1.0-rc.29`.

**Behavioral compatibility.** No accept/reject verdict changes; no wire bytes change. The reference implementation at samjanny/entangled-api already follows reading (B): its `verify_canary` computes the canary state (including Expired) and returns it for the pipeline to carry forward, halting only on a structural `E_CANARY_INVALID`; the Expired render-block and the section 08:185 override live in the embedding client. It passes the rc.29 corpus unchanged.

**Wire format summary.** Unchanged. `spec_version` remains `"1.0"`. The change is precedence/placement prose in section 10 plus a corpus-README correction; no diagnostic-catalog, schema, or vector-byte change.

### v1.0-rc.28

Date: 2026-05-29

**Lotto 28 - origin.carrier and origin.address rejection codes (AMB-10, AMB-11)**

Closes issues #11 (AMB-10) and #12 (AMB-11) on the repository. Both pin a Stage 5 rejection code that the normative text left open and that two conforming implementations could otherwise disagree on for identical wire bytes. No wire-format, schema, signature-input, JCS, NFC, byte-cap, or new-code change; `spec_version` remains `"1.0"`. The diagnostic catalog gains one example under an existing code; no codes are added or removed. The reference implementation already produces both pinned codes (its `Carrier` serde enum yields the enum-violation code on an unknown variant, and its `OnionAddress` newtype rejects a non-lowercase body at Stage 5 field deserialization), so this rc aligns the spec to existing behavior with no implementation change.

Like the first-wave AMBs, both are schema-dispatch ambiguities surfaced by reading the spec fresh: the text said the manifest MUST be rejected but did not pin which Stage 5 code reports the rejection.

**AMB-10 / issue #11: bad `origin.carrier` value.** Section 06 requires `origin.carrier` to be exactly `tor-v3` but did not name the code for a syntactically valid non-member (for example `"i2p"`). `E_SCHEMA_FIELD_SYNTAX` (a string violating its declared syntax: slug, base64url, RFC 3339, path) does not fit; `carrier` is a closed value set, and a valid string outside it is the textbook enumerated-set violation, the same class as an unknown state-policy `mode` or transaction `feedback` `variant` already listed under `E_SCHEMA_ENUM_VIOLATION`. Section 06 now states that a non-`tor-v3` `carrier` (and `migration_pointer.successor_origin.carrier`) is rejected at Stage 5 as `E_SCHEMA_ENUM_VIOLATION`, and the section 11 `E_SCHEMA_ENUM_VIOLATION` catalog row adds `carrier` to its examples.

**AMB-11 / issue #12: non-canonical (uppercase) `origin.address`.** Section 06 lists "56-character lowercase base32 ... `.onion`" as the `origin.address` field format but then deferred "exact validation" to section 05, whose Stage 9 binding step (key derivation and fetched-vs-declared comparison) folds in the canonical-form requirement. This left it open whether an uppercase-base32 `origin.address` is a Stage 5 field-syntax failure (`E_SCHEMA_FIELD_SYNTAX`) or a Stage 9 binding failure (`E_BIND_ORIGIN`) - a stage AND code divergence on identical wire bytes. Section 06 now states that the lowercase-base32 / 56-character / `.onion` shape is a declared field syntax validated at Stage 5 as `E_SCHEMA_FIELD_SYNTAX`, that case is part of the canonical wire form (one canonical encoding per address, like the fixed `sha-256:` prefix and base64url alphabets elsewhere), and that the section 05 Stage 9 binding operates on an already-canonical address and covers only key derivation and the fetched-vs-declared comparison (failing as `E_BIND_ORIGIN`). This keeps the Stage 5 / Stage 9 separation that AMB-05 established and does not re-mix the two layers.

**Corpus.** Two new negative vectors in the Stage 5 origin-field range: `144-schema-carrier-enum-violation` (`carrier: "i2p"` -> `E_SCHEMA_ENUM_VIOLATION`) and `145-schema-address-uppercase-syntax` (uppercase base32 `origin.address` -> `E_SCHEMA_FIELD_SYNTAX`). Both manifests are re-signed over the mutated payload so the signature verifies and the schema violation is the only live Stage 5 violation; vector 145 is distinct from vector 175 (`E_BIND_ORIGIN`), which exercises a genuine key-derivation mismatch with both addresses lowercase. No existing vector input bytes change; the count moves 62 -> 64; `corpus.json` `rc_target` moves `1.0-rc.27` -> `1.0-rc.28`.

**Behavioral compatibility.** Both rejections were already required by section 06 (the manifest MUST be rejected); this rc only pins which Stage 5 code reports them. A conforming implementation that already rejected these manifests now reports `E_SCHEMA_ENUM_VIOLATION` (carrier) and `E_SCHEMA_FIELD_SYNTAX` (address) at Stage 5. The reference implementation at samjanny/entangled-api already produces exactly these codes and stages, so it needs no change beyond the `SPEC_REVISION` bump.

**Wire format summary.** Unchanged. `spec_version` remains `"1.0"`. No schema, signature-input, JCS, NFC, byte-cap, or transport change; one example string is added to an existing diagnostic-catalog row and two Stage 5 rejection codes are pinned in section 06.

### v1.0-rc.27

Date: 2026-05-29

**Lotto 27 - exact-decimal integer serialization above 2^53**

Pins the canonical serialization of Entangled integers to exact decimal across the whole admitted range `[0, 2^63 - 1]`, including integers above `2^53`, overriding the IEEE 754 binary64 interpretation the JCS profile would otherwise apply. No wire-format, schema, signature-input, NFC, byte-cap, or diagnostic-catalog change; `spec_version` remains `"1.0"`. This is a clarification: it makes a serialization rule explicit that the reference implementation already follows.

Section 04 specified deterministic number serialization "following the ECMAScript number-to-string rules for IEEE 754 double-precision values within the I-JSON range" (04:23) and admitted integers up to `2^63 - 1` (04:77), but it gave no serialization-output rule for integers in `(2^53, 2^63 - 1]`, which have no exact binary64 representation. The parser-level discussion at 04:83-86 is input-scoped (it forbids a binary64-first parser from accepting an over-2^53 token and silently rounding it) and does not pin the output side. Two conforming implementations could therefore serialize the same admitted integer differently (exact decimal vs binary64-rounded), producing divergent canonical bytes and incompatible signatures for the same document. A `content.seq` value is an unbounded `u64` in the schema, so the band is reachable.

**Section 04 integer serialization rule.** A new "Integer serialization" subsection states that the canonical serialization of an Entangled integer is its exact shortest decimal form across the whole `[0, 2^63 - 1]` range, including above `2^53`, and that such an integer MUST NOT be routed through a binary64 conversion for serialization. The grammar already forbids the corresponding input forms; this pins the output side so two conforming implementations produce identical canonical bytes (and identical signature input).

**Corpus.** New positive vector `007-content-valid-large-seq`: a content document with `seq = 9007199254740993` (`2^53 + 1`, the smallest integer with no binary64 representation), signed by `K_runtime` over the exact-decimal canonical form. A conforming verifier accepts it; an implementation that serializes the seq through a binary64 double emits `9007199254740992` and fails signature verification. The corpus count moves 61 -> 62; no existing vector input bytes change; `corpus.json` `rc_target` moves `1.0-rc.26` -> `1.0-rc.27`.

**Behavioral compatibility.** No accept/reject verdict changes for any rc.26 document and no wire bytes change. The rule pins behavior the reference implementation at samjanny/entangled-api already follows (it serializes integers as exact decimal via the native u64 path, with no binary64 conversion), so the implementation needs no change beyond the `SPEC_REVISION` bump. An implementation that had chosen a binary64 serialization path for the supra-2^53 band is non-conformant under this rule, as it always was against the 04:83-86 parser rule on the input side.

**Wire format summary.** Unchanged. `spec_version` remains `"1.0"`. No schema, signature-input definition, NFC, byte-cap, transport, or diagnostic-catalog change; the canonical-bytes rule is made explicit for a range the grammar already admitted.

### v1.0-rc.25

Date: 2026-05-29

**Lotto 25 - migration_pointer successor address-to-key binding diagnostic**

Adds a closed `details.reason` value for the existing `E_MIGRATION_INVALID` code so that the section 06 announcement-internal successor binding check has a normative diagnostic identifier. No wire-format, schema, signature-input, JCS, NFC, byte-cap, or new-code change; `spec_version` remains `"1.0"`. The diagnostic catalog gains one closed-enum `reason` value; no codes are added or removed.

Section 06:383 already requires, for Tor v3, that `successor_origin.address` decodes to a public key equal to `successor_origin.origin_pubkey` (the same address-to-key binding rule as for the top-level `origin`, per section 05), and that the client verify this before treating the announcement as valid. This is an announcement-internal check on the two declared fields of the `migration_pointer`; it does not fetch the successor and is evaluated when the announcing manifest is validated. It is distinct from the section 10 fetch-time successor checks, which compare the fetched successor manifest's own `origin` fields against the announced `successor_origin` and fail as `E_MIGRATION_MISMATCH`.

Before this rc, the section 06:383 binding failure had no diagnostic identifier: the `E_MIGRATION_INVALID` `details.reason` vocabulary in section 11 was a closed set (`self_pointer`, `announced_at_after_updated`, `carrier_mismatch`, `chain_cycle`) with no value for the successor binding, while the `address` / `origin_pubkey` `mismatch_field` values under `E_MIGRATION_MISMATCH` belong to the section 10 fetch-time check, a different stage. An implementation enforcing 06:383 therefore had no conformant way to report it.

**Section 11 `reason` vocabulary extension.** `details.reason` for `E_MIGRATION_INVALID` gains the closed value `successor_key_mismatch`: "for Tor v3, `migration_pointer.successor_origin.address` does not decode to a public key equal to `migration_pointer.successor_origin.origin_pubkey`; the announcement-internal address-to-key binding of section 06". The `E_MIGRATION_INVALID` catalog row is extended to list this case. The reason vocabulary remains closed; this adds one member.

**Section 06 cross-reference.** Section 06:383 is extended to state that the binding failure is `E_MIGRATION_INVALID` with `details.reason = "successor_key_mismatch"`, that it is announcement-internal (no successor fetch), and that it is distinct from the section 10 fetch-time `E_MIGRATION_MISMATCH` checks.

**Corpus.** New vector `202-migration-successor-key-mismatch` (single manifest, announcement-internal): the `successor_origin.address` is the onion address of `origin_pub_2` while the declared `successor_origin.origin_pubkey` is `origin_pub`, so the address does not decode to the declared key. Verdict `reject`, diagnostic `E_MIGRATION_INVALID`, `details.reason = "successor_key_mismatch"`. No existing vector input bytes change; the `vectors/` tree gains one directory and the corpus count moves 60 -> 61. The `200-209` category note in `corpus/README.md` is extended to mention the new reason. `corpus.json` `rc_target` moves `1.0-rc.24` -> `1.0-rc.25`.

**Behavioral compatibility.** The section 06:383 binding requirement is unchanged; this rc only gives its failure a diagnostic identifier. A client that already enforced 06:383 now reports it as `E_MIGRATION_INVALID` / `successor_key_mismatch` instead of an implementation-chosen code. The reference implementation at samjanny/entangled-api implements the check at this rc (it was previously unenforced at the announcement level). No rc.24 document's accept/reject verdict changes except that an announcement whose successor binding is inconsistent, previously not checked at announcement time by that implementation, is now rejected at validation rather than only at the section 10 fetch step.

### v1.0-rc.24

Date: 2026-05-29

**Lotto 24 - normative-reading clarifications for seven specification ambiguities (AMB-01 through AMB-08)**

Closes issues #2 (AMB-01), #3 (AMB-02), #4 (AMB-03), #5 (AMB-04), #7 (AMB-06), #8 (AMB-07), and #9 (AMB-08) on the repository. Each issue identified a point where the spec admitted two readings under which two conforming implementations could diverge on a diagnostic code, an accept/reject verdict, or a budget computation, with no non-conformance on either side. None of the seven was a behavior bug in the protocol; each was an underspecified normative reading. The Rust reference implementation at samjanny/entangled-api already commits to one reading per ambiguity, and every clarification in this rc pins the spec to the reading the implementation takes, so no implementation change is required. There is no wire-format, schema, signature-input, JCS, NFC, byte-cap, or diagnostic-catalog change; all rc.23 documents validate identically under rc.24.

**AMB-01 / AMB-02: content-index transport-code precedence (issues #2, #3).** For the `/content_index.json` resource, the content-index-specific code `E_CONTENT_INDEX_FETCH_FAILED` displaces the generic Stage 1 transport codes. The spec previously assigned `E_CONTENT_INDEX_FETCH_FAILED` to a missing `Content-Length` (09:106) and to a present `Content-Encoding`/`Transfer-Encoding` (09:108) but did not state that this assignment displaces the generic `E_TRANSPORT_CONTENT_LENGTH` / `E_TRANSPORT_CONTENT_ENCODING` / `E_TRANSPORT_TRANSFER_ENCODING` / `E_TRANSPORT_CONTENT_TYPE` codes that the Stage 1 classification would otherwise produce. Two implementations could emit different codes on the same wire condition depending on whether they branched on the resource path before or after Stage 1 classification. Section 09 ("Content index fetch") and section 11 (after the content-index code rows) now state explicitly that every transport violation on this resource maps to `E_CONTENT_INDEX_FETCH_FAILED`, regardless of branch order. This matches the caller-obligation documentation already in the implementation's `validation/content_index.rs` module docs (PR5, audit finding M-4). One paragraph closes both issues.

**AMB-03: empty content-index `entries` map (issue #4).** The content-index closed schema accepts `{"entries":{}}` structurally, but section 02 did not say whether an empty map is a meaningful state or a semantic violation. Section 02 ("Content index schema") now states that an empty `entries` map is permitted and meaningful: it asserts that the publisher has committed to no content paths under `content_root`, the `content_root` commitment is in force but no path is currently protected, and a client MUST accept it as valid. The `content_root` hash binding still binds the exact bytes of the empty index. This is reading (a) of the issue and matches the implementation, where `ContentIndex::is_empty()` is a public, documented accessor for a legitimate state.

**AMB-04: code precedence when content `seq` is absent and the index fetch already failed (issue #5).** When the `/content_index.json` fetch has failed (`E_CONTENT_INDEX_FETCH_FAILED`) and a content document then arrives without `seq`, both that code and `E_CONTENT_SEQ_MISSING` nominally applied; the spec did not order them. Section 09 (at the 09:114 hard-fail) and section 11 now state that when `E_CONTENT_INDEX_FETCH_FAILED` has been emitted for a manifest, the per-document content-index checks (`E_CONTENT_SEQ_MISSING`, `E_CONTENT_HASH_MISMATCH`, `E_CONTENT_SEQ_ROLLBACK`, `E_CONTENT_SEQ_UNCOMMITTED`) are not evaluated against that manifest - there is no verified content index to evaluate them against - and the surface diagnostic for the content-rendering block remains `E_CONTENT_INDEX_FETCH_FAILED`. The per-document checks resume only once a content index has been fetched, hash-verified, and structurally validated. This matches the implementation, where `verify_content_against_index` requires a `ContentIndex` argument that a failed fetch never produces.

**AMB-06: 5-year `origin.not_after` ceiling across canary rotations (issue #7).** Section 06 imposes a 5-year ceiling on `origin.not_after` relative to `canary.issued_at` but did not say, across a rotation that carries a new `canary.issued_at`, whether the window slides forward or stays anchored to a first-declared value. Section 06 now states that the ceiling is evaluated per manifest, relative to that manifest's own `canary.issued_at`: the window slides forward with each rotation, and the effective lifetime of a continuously-rotated origin is not bounded by any single ceiling. The rationale is added: the ceiling bounds an unrotated (stale) origin, whose window is anchored to the last canary a client can have verified; a publisher that keeps rotating is demonstrating liveness, and a publisher wanting a bounded total lifetime enforces that operationally by not advancing `not_after`. This is reading (a) and matches the implementation, which checks the horizon against the current manifest's own `canary.issued_at` at build/parse time (`ORIGIN_NOT_AFTER_MAX_HORIZON_SECS`).

**AMB-07: which side of the submit-budget partition the JSON wrapper bytes fall on (issue #8).** Section 09's submit-body partition (`overhead_reserve + field_min_reserve + state_budget = 65536`) did not say whether the `"request_state":` / `"fields":` member names, their colons, and the surrounding `[]` / `{}` brackets count against `overhead_reserve` or against the per-array budget. Section 09 now states that these array-wrapper bytes are envelope bytes and count against `overhead_reserve`; only the per-entry payload bytes and the inter-entry commas count against `state_budget` (for `request_state`) or `field_min_reserve` (for `fields`). A publisher tuning a policy to fill `state_budget` therefore accounts only for the per-entry contributions and inter-entry commas. This matches the implementation's `aggregate_request_state_bytes`, where each entry contributes a fixed 36-byte object envelope plus `namespace`/`key`/`value` lengths plus one comma per inter-entry boundary, with the array wrapper provided for in the 4096-byte `SUBMIT_OVERHEAD_RESERVE_BYTES`.

**AMB-08: unit of the per-value `max_size` cap (issue #9).** Section 07:164 defined `max_size` as a size "in bytes" and section 09:217 as "not exceeding 4096 bytes" without saying whether the unit is the value's raw UTF-8 byte length or its JSON-escaped wire length. The two differ for values containing `"`, `\`, or control characters, which expand under JSON escaping. Section 07 (`max_size`) and section 09 (request_state schema) now pin the unit to the raw UTF-8 byte length of the value, measured before JSON escaping; the cap is on the value's own bytes and does not require serializing the value first. This is reading (a) and matches the implementation, which checks `value.len()` (a raw UTF-8 byte length) against the cap and plugs the raw `max_size` into the Stage 5 budget aggregate with no escape expansion. The §07:111 aggregate definition is corrected to state that the `value` is counted at its raw `max_size` and is not escape-expanded for the aggregate (the prior wording said "the worst-case `value` string with the same encoding rules", which read as escape-expansion and disagreed with the implementation).

To keep the two-level submit-budget partition introduced in Lotto 21 unambiguous, this rc also adds a normative necessary-vs-sufficient statement in section 07 and section 09 and a publisher headroom guideline in the operator playbook. The Stage 5 `E_SUBMIT_BUDGET` aggregate is a necessary, envelope-level condition on the declared `state_policy`: it bounds the policy assuming retained values do not expand under escaping. It is not sufficient, because a concrete value's escaped wire form can exceed its raw `max_size` contribution. The runtime `E_STATE_TRANSMIT_BUDGET` check is the sufficient condition: it measures the actual escaped wire bytes of retained values at submit time. The playbook adds a "Sizing max_size with wire headroom" subsection advising publishers to size `max_size` with margin for escape-bearing values (up to roughly 6x on the wire for control characters), since a submit that exceeds the partition is rejected at runtime even when the policy passed the Stage 5 check.

The single submit-budget vector (143-submit-budget-state-overflow) already counts the worst-case `value` at its raw `max_size` with no escape expansion, so it is already correct under the AMB-08 reading; its generator comment and `corpus.json` description are sharpened to state the raw-UTF-8-byte accounting explicitly and to note that the escape-sensitive per-value wire boundary lives in the deferred `E_STATE_TRANSMIT_BUDGET` runtime path. `corpus/README.md` gains the same note in the deferred-State bullet. `corpus/tools/generate.py` was rerun and produces a byte-equal `vectors/` tree; the only generated change is the `rc_target` field in `corpus.json` (`1.0-rc.23` -> `1.0-rc.24`).

**Lotto 22 - §05:174 small-order R rejection alignment (N63)**

Closes issue #1 on the repository, which reported a factual error in §05:174: the pre-N63 text claimed that the `verify_strict` mode in `ed25519-dalek` does not apply small-order rejection to the signature `R` component, and that the protocol matches that behavior by also accepting small-order `R`. Both clauses are factually wrong: `ed25519-dalek 2.2.0` (`src/verifying.rs`, the `verify_strict` function) explicitly rejects a signature when either `signature_R.is_small_order()` or `self.point.is_small_order()` holds, before evaluating the cofactorless verification equation. An implementation that followed §05:174 literally and used `verify_strict` (the natural choice, since §05 itself names it as the reference) therefore rejected signatures that the spec's prose declared conformant, producing a cross-implementation conformance gap.

The error was introduced at rc.18 N34 (Lotto 8), which added the §05:174 clarification on the basis of a misreading of dalek's source. Subsequent rc audit passes (including a multi-agent verification round) did not catch the error because the verification step compared §05 against itself rather than against the cited library source. The issue was discovered when an independent Rust implementation built against `verify_strict` and observed the divergence in practice.

The fix is Option A from the issue: align the spec to the de facto `verify_strict` behavior. Rejecting small-order `R` is strictly safer (it tightens; it does not weaken), removes the cross-implementation divergence, and matches what the reference library actually produces. The alternative (Option B - keep the protocol intent of accepting small-order `R` and remove the dalek reference) was rejected because the original "intent" was itself based on a misreading; preserving a fictional design rationale would complicate implementer guidance for no security or correctness benefit.

**§05:174 rewrite (N63)** - The paragraph is rewritten. The pre-N63 text said the small-order rejection applies only to `A` and that small-order `R` is accepted. The N63 text makes the small-order rejection apply to both `A` and `R`: a signature whose `R` decodes to a point of order dividing 8 MUST be rejected with `E_SIG_VERIFICATION` (§11), before or alongside the canonical-encoding / `S < L` / cofactorless-equation checks. The paragraph explicitly cites the dalek source location (`signature_R.is_small_order()` in `src/verifying.rs`) so future verification can check the spec against the library directly. A closing sentence motivates the rejection symmetry as required for cross-implementation determinism.

**§05:188 compatibility note extended (N63)** - The "Compatibility note" subsection that enumerates the verification practices the strict profile is incompatible with previously listed "accept small-order public keys without rejection" but did not list "accept signatures whose `R` component is a small-order point". The latter is added as a separate bullet; the existing bullet on `A` is clarified to say "public keys (`A`)" for symmetry with the new bullet on `R`. No further changes to §05.

**Corpus vector 157 (N63)** - New single-document vector `157-sig-small-order-r`: a manifest whose signature `R` component is replaced with the encoded identity point (the same SMALL_ORDER_A pattern that vector 153 uses for the public key `A`). The `S` half of the signature is left at the original valid value; the small-order `R` rejection takes precedence. Expected reject + `E_SIG_VERIFICATION`. ### v1.0-rc.21

Date: 2026-05-28

**Lotto 21 - submit budget invariants (N62)**

A post-rc.20 audit pass identified a protocol incoherence in the submit body cap interaction with `state_policy` declarations. The 64 KiB submit body cap (§09) must hold the mandatory `request_state` load (§07 requires the client to include all non-expired request-mode items in every submit) plus the user-entered `fields` portion plus the JSON envelope. With the pre-N62 caps, a conforming publisher could declare a `state_policy` with 32 request-mode entries each capped at 4096 bytes, for a worst-case aggregate of 128 KiB - twice the submit body cap. No eviction rule existed (deliberately, since eviction breaks auth semantics non-deterministically), so a compromised `K_runtime` filling state to the declared maxima could permanently deadlock all future submits for that publisher's clients.

The pre-N62 spec already had a runtime client-side soft-fail rule (`E_STATE_TRANSMIT_BUDGET`, §07 "Request-state transmit budget", §11) that rejects an individual `set` operation when the minimal submit body would overflow. This is necessary but insufficient: it prevents the client from drifting into an unsatisfiable state under a satisfiable policy, but it does not prevent a publisher from declaring an unsatisfiable policy in the first place. Under such a policy every `set` would be rejected by the client; the feature would be undeclarable rather than just runtime-protected.

Lotto 21 closes the gap by defining a normative budget partition in §09 and a satisfiability invariant in §07 that rejects an unsatisfiable manifest at Stage 5 schema validation.

**§09 submit body budget partition (N62)** - A new normative paragraph in §09 partitions the 64 KiB submit body cap into three reserves: `overhead_reserve + field_min_reserve + state_budget = 65536 bytes`. The values are `overhead_reserve = 4096` bytes (for `request_id`, `in_response_to`, JSON envelope, and a margin for future additive envelope fields), `field_min_reserve = 8192` bytes (a reserve, not a cap, for the user-entered `fields` portion), and `state_budget = 53248` bytes (the budget against which a manifest's `state_policy` declared aggregate is evaluated at validation per §07). The partition is defined in encoded wire bytes, not raw value sizes; an implementation that conflates the two underestimates the wire load and can declare conformant a policy that is in fact over-budget. The specific split values reflect a normative judgment about how much mandatory request-state load is reasonable per submit; 53248 bytes (about 81% of the cap) reflects that mandatory state is the load class that triggers the deadlock the partition is designed to prevent, while `field_min_reserve = 8192` is sized to cover a minimal form (per §03, no `min_length` exists, so required fields can be near-empty; 8 KiB is comfortably above the worst-case minimal form), and `overhead_reserve = 4096` is generous against an envelope that in practice fits in a few hundred bytes. The split MAY be re-tuned in a future protocol version; v1.0 fixes the values above.

**§07 submit budget satisfiability invariant (N62)** - A new normative subsection in §07 defines the satisfiability invariant: a manifest's `state_policy` whose aggregate worst-case encoded wire contribution exceeds `state_budget` (§09) MUST be rejected at Stage 5 schema validation as `E_SUBMIT_BUDGET` (§11) with `details.component = "state"`. The aggregate is computed over all `mode = request` entries assuming each entry's retained `value` is at its declared `max_size`, including JSON quoting/escaping and array delimiters. Client-only entries do not contribute (they are never transmitted). The check is deterministic and computable from the manifest payload alone; it does not depend on the client's current retained state. The subsection explicitly distinguishes the satisfiability invariant (Stage 5 manifest validation) from the runtime client-side `E_STATE_TRANSMIT_BUDGET` rule (soft-fail on individual `set` operations): both are required, the former rejects unsatisfiable contracts, the latter prevents runtime drift under satisfiable contracts.

**§11 new diagnostic `E_SUBMIT_BUDGET` (N62)** - New error-class Stage 5 diagnostic added to the Schema diagnostics catalog, document_kind = manifest. Structured `details` schema includes `component` (`"state"` is the only v1.0 value; the field is present and explicit for future-extensibility, mirroring the pattern of `E_ORIGIN_INVALID.reason` and `E_CANARY_RUNTIME_REUSE.window_position`), `declared_bytes` (the computed aggregate), and `budget_bytes` (the applicable limit, 53248 for `component = "state"`). The new code is distinct from `E_STATE_TRANSMIT_BUDGET` in detection stage and scope (validation vs runtime, manifest vs transaction-document); both codes remain in v1.0 catalog because they cover non-overlapping failure modes.

**Form fields side - no §03 change in this lotto.** The user audit raised a parallel concern that `submit_form` field `max_length` aggregates can also exceed the submit body cap (16 fields x 8192 bytes = 128 KiB worst case in §03; up to 32 x 8 KiB = 256 KiB at the §09 wire transport limit). The form fields side is intentionally NOT given an analogous Stage 5 invariant because form fields are a *user-chosen ceiling*, not a *mandatory load*: `max_length` is a per-field ceiling that the user MAY use, not a load the client MUST transmit. Applying a "sum of field max_lengths <= field_min_reserve" rejection would wrongly forbid legitimate forms with generous per-field ceilings (e.g., one 8 KiB textarea plus 15 small fields fits any real submit). The form fields side is therefore covered by the §09 `field_min_reserve` partition (which guarantees a minimally-submittable form always fits alongside maxed state) plus the existing §03:866 runtime block on oversize submits, which is the correct handling for actual field overflow. No new diagnostic for the fields side is added in this lotto; the §03 surface remains unchanged. The §09 partition includes a reconciliation note clarifying that the §09 `fields`-object 32-key transport-level upper bound and the §03 `submit_form` 16-field declarative cap are layered, not contradictory.

**Corpus expansion (N62)** - One new vector added at `corpus/vectors/143-submit-budget-state-overflow/`: manifest declaring 32 request-mode `state_policy` entries each with `max_size = 2048` bytes, producing an aggregate encoded contribution of 66879 bytes (32 entries times (2048 value bytes plus ~39 envelope bytes) plus 31 commas), exceeding the 53248-byte `state_budget` by 13631 bytes. Expected verdict: reject, diagnostic `E_SUBMIT_BUDGET`, `details.component = "state"`. The manifest is signed correctly and otherwise valid; the satisfiability violation is the only live Stage 5 violation. This is a single-document validation vector and does NOT require the deferred submit-flow vector-schema extension. Total corpus: 58 -> 59 vectors. Distinct-code coverage: 36 -> 37 (E_SUBMIT_BUDGET is the new code). `corpus/README.md` Categories table extends the 140-149 row to include "Stage 5 semantic (submit budget state overflow)"; the "State" coverage gap note documents that the Stage 5 manifest-validation portion is now covered while runtime `E_STATE_*` codes remain deferred to the submit-flow extension.

**Corpus `rc_target` bump 1.0-rc.20 -> 1.0-rc.21.** The corpus index's `rc_target` field is bumped to identify the rc.21 conformance profile. Unlike the rc.19 -> rc.20 bump (which was metadata-only and the conformance profile was byte-identical), rc.21 introduces a genuine normative tightening (`E_SUBMIT_BUDGET` is new, and a previously-conformant manifest with an over-budget `state_policy` is now non-conformant).

**Diagnostic catalog summary.** One new error code: `E_SUBMIT_BUDGET` (Stage 5, manifest, error severity). All other catalog entries unchanged. Total v1.0 catalog: prior count + 1.

**Wire format summary.** Unchanged. `spec_version` remains `"1.0"`. No schema additions or removals on any document kind. JCS canonicalization, NFC, byte caps, and all other input restrictions are unchanged. All rc.20 documents validate identically under rc.21 EXCEPT those manifests whose `state_policy` aggregate exceeds `state_budget`; those manifests are non-conformant under rc.21 (the deadlock they would have produced under rc.20 was an unintended consequence of underspecified caps).

**Behavioral compatibility.** Normative tightening: an rc.20 manifest declaring a `state_policy` whose aggregate encoded worst-case contribution exceeds 53248 bytes is non-conformant under rc.21 and is rejected as `E_SUBMIT_BUDGET` at Stage 5. The tightening closes a deadlock vector; publishers operating well below the cap (the typical case: a handful of small request-mode entries) are unaffected. An rc.20 client that did not implement the satisfiability check accepted the unsatisfiable manifest and then rejected every `set` operation under the runtime `E_STATE_TRANSMIT_BUDGET` rule; the user-facing experience was a feature that never worked. Under rc.21 the manifest is rejected upfront with a precise diagnostic identifying the misconfiguration. Publishers SHOULD review their `state_policy` declarations against the 53248-byte aggregate budget; deployments using only a few small request-mode entries (typical session-token, language-preference, checkout-state use cases) are well under budget.

**Lotto 15 - errata (N56-N58)**

A seventh-pass audit (multi-agent verification of audit findings against current spec text) surfaced three textual issues with no impact on wire format, schema, or the diagnostic catalog: a typo in a `details.reason` identifier, a contradiction between §10 and §11 on the chain-depth handling, and an ordering defect in the §08 canary ceremony step list. **§11 `E_ORIGIN_INVALID.details.reason` typo - `not_after_not_after_issued_at` -> `not_after_not_later_than_issued_at` (N56)** - The §11 structured diagnostic format for `E_ORIGIN_INVALID` listed two `reason` identifiers, one of which contained an obvious stutter (`not_after_not_after_issued_at`). **§11 `E_MIGRATION_INVALID` triggers - chain-depth removed, `chain_cycle` added, structured `details` documented (N57)** - The §11 row for `E_MIGRATION_INVALID` previously listed "chain depth exceeded" as one of the triggering conditions (qualified as "for clients enforcing the chain-depth rule"). This contradicted §10:442, which states that reaching the automatic chain-depth limit produces a *pending user action* state (recoverable by user confirmation), not a hard rejection with a diagnostic. The contradiction was also a category error: §11 defines `E_MIGRATION_INVALID` as a property of the document ("structurally valid JSON but fails semantic checks"), whereas chain-depth-exceeded is a property of the client's local traversal budget, configurable per §10:435,440 and therefore non-deterministic for the same input across conforming clients. The §11 row is updated by swap: the "chain depth exceeded" trigger is removed, the `chain_cycle` trigger (defined in §10:436 but previously absent from the §11 trigger list) is added, and a new clarifying sentence states that reaching the automatic chain-depth limit is not a semantic failure and does not produce this diagnostic. A new structured-diagnostic-format block for `E_MIGRATION_INVALID` is added immediately after the `E_MIGRATION_MISMATCH` block, documenting `details.reason` (drawn from `self_pointer`, `announced_at_after_updated`, `carrier_mismatch`, `chain_cycle`), `announcing_origin_address`, and `successor_origin_address`. §10 is not changed in behavior; the §10:435 prose is separately disambiguated under N57 to state explicitly that "automatic adoption" in the chain-depth subsection means following a hop without re-prompting on the basis of a confirmation already obtained earlier in the flow, never a first-time adoption without confirmation (the initial `A -> B` adoption always requires user confirmation per §10:404, §10:410, §10:411). The disambiguation does not change client behavior; it removes a literal-reading inconsistency between §10:435 ("automatically adopt one hop without re-prompting") and §10:404/410/411 (user-confirmation MUST for all trust states). Resolves the cross-section contradiction without changing wire format, validation behavior, or the diagnostic catalog.

**§08 Canary ceremony step ordering - reversible signing cutover precedes irreversible manifest deploy (N58)** - The §08 canary ceremony step list had two defects. First, steps 5 and 6 both stated "Deploy the new manifest", with step 5 also instructing the operator to "make the new `K_runtime_priv` available to the publishing infrastructure" - a duplicated deploy instruction. Second, the configuration of the publishing infrastructure to sign with the new `K_runtime_priv` was placed in step 7, *after* the manifest deploy in step 6. Steps 5, 6, 7 are restructured: step 5 transfers `K_runtime_priv` to the publishing infrastructure and configures the infrastructure to sign new content and transaction documents with it, without deploying the new manifest yet; step 6 deploys the new manifest at `/manifest.json`; step 7 destroys the previous `K_runtime_priv`. The structural reason: a signature-verification window is inherent to single-runtime-key rotation (clients holding a cached prior manifest verify against the previous `K_runtime.pub`; clients fetching the new manifest verify against the new `K_runtime.pub`; the publisher's signing configuration can only point at one private key at a time, and no protocol mechanism in v1 supports dual-key overlap on the published side). The reordering does not eliminate the window; it minimizes its duration when steps 5 and 6 are performed in immediate succession (ideally atomically), and - more importantly - it places the *reversible* step (the signing-configuration switch in step 5, which can be reverted at the publisher's discretion as long as no client has observed the new manifest) before the *irreversible* step (the manifest deploy in step 6, which the moment any client observes it commits the new `canary.issued_at` under §08:65 anti-downgrade enforcement and prevents the publisher from rolling back to the previous manifest under the same `K_publisher`). The pre-N58 order had the irreversible step first: if the signing cutover then failed, the publisher was trapped between a deployed manifest whose `K_runtime.pub` no infrastructure could match and an anti-downgrade rule that prevented serving the previous manifest. The new order eliminates that trap. No wire-format or schema change.

**Lotto 17 - operator playbook hardening (no spec changes)**

A seventh-pass audit (Agent 5 operational security) identified thirteen gaps in `docs/operator-playbook.md` that the existing rc.18 playbook acknowledged only vaguely or not at all. Lotto 17 adds eleven new subsections to the playbook closing those gaps. The playbook is non-normative; these changes do not affect protocol conformance. They shift the operator's posture from informal "do something secure here" toward concrete, auditable practices that a third-party operator review can verify.

The Lotto 17 additions, by §-section of the playbook:

**§3.1 Backup encryption scheme (closes F11)** - The pre-Lotto-17 §3.1 said "encrypted backups" with no concrete tool or KDF guidance. The new "Backup encryption scheme" subsection requires a concrete tool (age, GPG symmetric with explicit S2K parameters, or age with an SSH/X25519 recipient), explicit passphrase entropy (>= 80 bits, with practical generation from EFF diceware or random 14+ char strings), separate passphrase storage, and explicit prohibitions on ad-hoc OpenSSL encryption, zip/7z passwords, and full-disk-encryption-alone.

**§3.1 Backup verification (closes F4)** - The pre-Lotto-17 §3.1 required backups but had no verification procedure. **§4 Witness and dual-control (closes F1)** - The pre-Lotto-17 §4 described a single-operator ceremony only. **§7 Pre-staging discipline (closes F2)** - The pre-Lotto-17 §7 said "rotate before next_expected" but had no preparation procedure. The new "Pre-staging discipline" subsection requires a post-ceremony checklist (offline machine bootable, backup decryption verified, fresh K_runtime candidate staged, witness availability confirmed, OOB templates pre-drafted, deployment dry-run completed) maintained continuously between ceremonies rather than executed on demand against the rotation deadline. For 7-day cadences the pre-staging is operationally load-bearing; for 14-30-day cadences it is recommended.

**§7 Freshness proofs (closes F13)** - The pre-Lotto-17 §7 mentioned `freshness_proof` as an optional ceremony input without operational guidance. The new "Freshness proofs" subsection defines when to include one (backdating-defense threat models), the four reference-event properties (public, unpredictable, externally timestamped, stable), three concrete reference options (bitcoin block header, major-outlet headlines, third-party git commits) ordered by ease of use, and explicit anti-patterns (publisher-controlled posts, NTP services, scheduled events). **§6 Out-of-cycle content correction at indexed paths (closes F12)** - The rc.19 N48 `content_root` freeze (§10:614) makes indexed paths immutable between ceremonies, but the pre-Lotto-17 §6 did not document how an operator responds to an urgent correction at an indexed path. **Lotto 19 - extended runtime-pubkey reuse check (N60)**

A seventh-pass audit (Agent 1) identified that the §08 `E_CANARY_RUNTIME_REUSE` check covers only the immediately preceding verified manifest, which leaves an `A -> B -> A` resurrection pattern (re-announcing a previously retired `runtime_pubkey` whose private key the §08 ceremony required to be destroyed) undetected. Lotto 19 adds a SHOULD-level extended check that clients maintaining publisher history reject any reuse against any previously verified `runtime_pubkey` for the same `K_publisher.pub`, with the existing diagnostic distinguished by a new `details.window_position` field. The MUST-level immediate-preceding check is unchanged, so stateless clients remain conformant.

The structural shape of the rule - publisher-history-based mitigation enforced where the client retains the necessary state, with a §00 limitation documenting the stateless gap - matches the existing pattern for cross-session migration history (§10 N20).

**§08 SHOULD extended runtime-pubkey window (N60)** - The §08 paragraph on the rotation-proof check is extended. The pre-N60 text required (MUST) rejection of `runtime_pubkey` reuse against the immediately preceding verified manifest for the same `K_publisher.pub`. The MUST is unchanged. A SHOULD is added: clients that maintain publisher history (the same publisher-history storage already used for anti-downgrade per §08:65 and for cross-session migration history per §10 N20) SHOULD reject a new manifest whose `runtime_pubkey` matches *any* previously verified entry in that history, with the same `E_CANARY_RUNTIME_REUSE` diagnostic. A clarifying paragraph in §08 establishes the rule's rationale: the §08 ceremony (steps 5, 7) and the operator playbook §3.3 require the prior `K_runtime_priv` to be destroyed at every rotation; a publisher able to re-announce a retired `runtime_pubkey` has either kept the corresponding private key in violation of the ceremony or is operating under conditions in which the ceremony discipline cannot be presumed (compromise, coercion). Clients with bounded storage MAY enforce a smaller window provided it remains at least the immediate-preceding entry; the MUST is not weakened. No protocol-level upper bound on the window in v1; storage cost is in the range of a few KB per publisher for typical rotation cadences.

**§00 limitation - extended runtime-pubkey reuse detection depends on implementation-defined publisher history (N60)** - A new entry is added to the §00 v1.0 limitations list, in the same structural shape as the existing cross-session migration cycle mitigation entry. Stateless clients that retain no publisher history across navigations cannot enforce the extended check and are not non-conforming on that basis; the universal MUST on immediate-preceding match still applies. The entry also notes the rule's defensive scope: it is defense-in-depth against publisher key-resurrection, not a defense against fully-compromised `K_publisher_priv` (an attacker with `K_publisher_priv` can announce all-fresh runtime keys and evade any reuse check by not reusing).

**§11 `E_CANARY_RUNTIME_REUSE` structured details extended (N60)** - The §11 row description for the diagnostic is rewritten to reference both the MUST (immediate-preceding) and the SHOULD (any-prior-history) cases. The structured `details` schema is extended with a `window_position` integer field: `1` denotes the immediate-preceding match (MUST-level rejection), `>= 2` denotes a deeper history match (SHOULD-level rejection), where `2` is the entry before the immediately preceding manifest, `3` is two entries before, and so on. This allows operators and conformance harnesses to distinguish "publisher failed to rotate" (window_position = 1) from "publisher resurrected a retired key" (window_position >= 2), the latter being a much more serious signal under the §08 ceremony's destruction discipline. Stateless clients that enforce only the MUST emit window_position = 1; stateful clients distinguish their diagnostics by this field.

**Lotto 20 - clock reliability and freshness-unverified mode (N61)**

A seventh-pass audit (Agent 2) identified that §10 prescribed a 300-second clock-skew tolerance without saying what a client should do when its local clock is itself unreliable: an unsynchronized device or one operating offline beyond a meaningful refresh window may exceed the tolerance on every check, either rejecting all current manifests as future-skewed (a recoverable false positive) or accepting any canary as fresh (a security failure). The pre-N61 text effectively assumed every client has a reliable clock; the audit observed that the protocol's anti-downgrade and freshness-determination requirements need explicit treatment for clients that do not.

Lotto 20 adds the §10 subsection "Clock reliability and the verified-time reference" defining client behavior when no reliable current-time reference is available, plus the corresponding §00 limitation, glossary entries, canary-table note, playbook signal-only note, and corpus README not-vector-constructible entry. The substance: anti-downgrade enforcement is unconditional (it is a relative check); a verified-time reference `T_verified` is an authenticated lower bound on real time, usable as a reference at fetch time and for drift detection but explicitly NOT a substitute for an offline clock and explicitly NOT the future-skew reference (lower bound where an upper bound is needed; using it as such deadlocks the client against its own stale reference after any offline period); a definitely-past expiration determination using `T_verified` is sound but incomplete (cannot establish expiry of the manifest the client holds); a client without a reliable clock enters freshness-unverified mode, an orthogonal presentation qualifier (not a sixth canary state) that suppresses the time-dependent Fresh/Near-expiration/Expired determinations and surfaces an explicit, not-easily-dismissible chrome indication that the current time cannot be placed within the canary's validity window.

The structural shape of the rule rejects two superficially attractive but wrong approaches: (a) using `T_verified` as the future-skew reference (rejected because it produces the deadlock described above; an offline client cannot accept any newly issued manifest), and (b) silently treating the canary as fresh in the absence of a clock (rejected because it converts a security determination into a covered-up unknown).

**§10 "Clock reliability and the verified-time reference" (N61)** - New subsection added immediately after "Clock skew tolerance". Six rules: anti-downgrade is unconditional; `T_verified` definition and properties (authenticated lower bound, useful at fetch and for drift, NOT an offline-time substitute, MUST NOT be the future-skew reference); drift advisory when local-clock and freshly verified `issued_at` diverge beyond the §10 skew tolerance (without rejecting the manifest on the divergence alone); sound lower-bound expiration determination using `T_verified` (sound but incomplete by construction for the held manifest); freshness-unverified mode for clients without a reliable current-time reference (no silent-fresh, no blind-block, explicit chrome indication, automatic recovery on successful refresh); and future-skew behavior without a reliable clock (no hard reject, loose sanity bound only, advisory).

**§10 canary state table note (N61)** - The five-value canary state machine (Fresh, Near-expiration, Expired, Invalid, Unavailable) is unchanged. A paragraph is added under the table clarifying that freshness-unverified mode is an orthogonal presentation qualifier, not a sixth state: it co-occurs with the time-independent determinations (Invalid, Unavailable, lower-bound Expired) which continue to govern rendering and chrome per the table, and suppresses only the time-dependent Fresh/Near-expiration/Expired verdicts. Anti-downgrade is unaffected.

**§00 v1.0 limitation (N61)** - A new entry is added to the §00 limitations list stating the irreducible substance: a client without a reliable current-time reference cannot verify canary freshness while offline; this is a property of the absence of a clock, not a protocol gap; such clients operate in freshness-unverified mode (§10), retain anti-downgrade and structural-validity guarantees, retain the sound lower-bound expiration determination using `T_verified`, and surface the freshness limitation in chrome. The entry explicitly notes that this limitation is intrinsic to operating without a current-time reference - a future protocol version cannot resolve it without supplying such a reference.

**§01 glossary (N61)** - Two new glossary entries: "Freshness-unverified mode" (cross-references §10, anti-downgrade, T_verified) and "Verified-time reference (`T_verified`)" (cross-references §10, anti-downgrade, freshness-unverified mode, issued_at).

**docs/operator-playbook.md §14 alerting (N61)** - A weak-diagnostic-signal note added to the §14 alerting subsection: reader reports of freshness-unverified mode are a *qualitative* signal, not an alert action. The condition is client-side and the publisher cannot remediate it. A correlated spike may indicate that the canary interval is longer than the reader-base online cadence (worth a §7 interval review) but may also be benign in deployments with many clock-less or intermittently-online readers. Do not alert on absolute rate.

**corpus/README.md not-vector-constructible (N61)** - The "not vector-constructible" section is extended to document freshness-unverified mode alongside `E_SIG_MALFORMED`: the trigger is a client-side property (no reliable current-time reference) that no document can induce; the corpus's wire-to-verdict mapping cannot exercise it. Conforming clients exercise the mode through their clock-acquisition path, not through any document the corpus could supply. No new vector is added.

**Coverage.** Lotto 20 closes audit Ag2 F14. No protocol or wire-format change. No new diagnostic codes (freshness-unverified is a chrome state, not an error). The canary state machine remains five values. The §10 300-second tolerance is unchanged. N56-N58 (Lotto 15): textual errata with no client-conformance impact. ### v1.0-rc.18

Date: 2026-05-28 (tagged retroactively at the final Lotto 10 commit; the rc.18 changes had been on `main` since the rc.17 soak window but the tag was cut later, when rc.19 was being prepared).

Changes since v1.0-rc.17 (which equals rc.16 plus the Lotto 6 playbook update and the README updates committed under `docs:` after the rc.16 retag):

This rc lands a textual errata tranche identified as Lotto 7 (ten low-severity clarifications aggregated into a single commit before tagging), a second-pass errata tranche identified as Lotto 8 (four additional low-severity clarifications driven by a fourth-pass audit, landed in a follow-up commit after Lotto 7), a third-pass errata tranche identified as Lotto 9 (four additional clarifications and limitation surfacings driven by a fifth-pass audit: one normative restructuring of the §10 migration successor adoption state, one §11 resolution of a versioning rule contradiction between §11 and the release engineering convention, two new §00 limitation entries surfacing previously-implicit v1.0 gaps), one follow-up clarification (N41) addressing a verified-pending edge case introduced by N37, a fourth-pass errata tranche identified as Lotto 10 (three normative-impact changes driven by a sixth-pass external cryptographic audit: a value-range narrowing on the canary interval, a SHOULD->MUST elevation on First-contact migration confirmation, and an additive submit-validation timing section), and a corpus Phase-1 coverage expansion (15 additional negative vectors filling previously-uncovered §11 diagnostic codes within the existing vector schema). No wire-format change; no schema change; the diagnostic catalog is unchanged. One existing diagnostic `details` field gains a precision constraint. Two SHOULD-level rules are tightened to MUST: the §10 cross-session migration history mitigation gains a recall-window upper bound and a directional fix (Lotto 9 N30/N31), and the §10 First-contact migration confirmation is elevated from SHOULD to MUST (Lotto 10 N43). One value-range MUST narrows: the §08 canary interval ceiling drops from 90 to 30 days (Lotto 10 N42). One §10 normative subsection (Successor verification) is restructured to introduce an explicit verified-pending successor state distinct from adopted; the restructuring makes the existing rc.17 staging of confirmation-gated actions unambiguous but does not add a new MUST that an rc.17 implementation correctly following §10:385 would not already satisfy. One additive §09 subsection (Submit validation timing) provides SHOULD-level guidance on server-side side-channel mitigation for the publisher submit-handling path (Lotto 10 N44).

**§10 Cross-session migration history - Replacement event covers the pre-Adoption current origin (N30)** - In rc.16 the `Replacement` event was recorded only when a previously adopted successor was itself superseded. This left a hole: the cross-session ping-pong vector `A -> B -> A -> B` was detectable in only one direction, because `A` (the original starting origin, never itself a successor before the first Adoption) was never marked as "previously replaced", so a later migration announcing `A` as a successor would not trigger the recall check. The Replacement event is now recorded in two situations: (a) at every Adoption, the pre-Adoption current origin (the announcing origin) is recorded as Replacement; (b) at the existing supersession case. Both directions of the ping-pong are now covered. The Replacement record schema is preserved; only the trigger conditions are extended.

**§10 Cross-session migration history - recall window upper bound (N31)** - The recommended 30-day recall window now has an explicit SHOULD-NOT-exceed of 365 days. Clients with bounded storage MAY enforce a smaller cap, whether by time or by event count (for example, the most recent 100 migration events per publisher profile, evicting the oldest first), provided the cap remains at or above the 7-day floor. Bounds the migration-history storage per publisher profile so that a long-lived `K_publisher.pub` does not accumulate unbounded events.

**§00 v1.0 limitations - publisher history portability (N32)** - Adds an explicit limitation entry stating that Entangled v1 does not specify a serialization format or migration mechanism for publisher history (trust-state pinning records, migration history, abandonment records). A user who switches client implementations resets these records and must re-establish them through PIP-confirmed out-of-band channels. The protocol's identity guarantees still hold across the switch (the new client treats the publisher as First contact); only cross-session continuity benefits are lost. Documents an existing v1.0 design choice rather than introducing one.

**§01 Glossary - `Rendering session` (N11)** - New glossary entry defines a rendering session as the lifetime of a single client commitment to render a specific document instance: it begins after Stages 6 through 9 succeed, ends on user-initiated reload, navigation away, or replacement of the underlying manifest by a newer one. In-flight retry attempts share the same session. Disambiguates the term used in §03 (no-retry rule for image verification failure) and §10.

**§08 Canary - `summary surface` aligned to §10 chrome terminology (N12)** - The §08 phrase "the canary's summary surface" is cross-referenced to §10 "Always-visible compact indicators" so implementations do not interpret the two terms as distinct UI surfaces. The complementary "expandable detail surface" of §10 is cited as the natural location for the contents of `freshness_proof`. No normative change; cross-reference clarification only.

**§10 Abandon retained publisher identity - deletion scope (N13)** - The `delete the active trust-state record for P` step is extended to enumerate what the deletion includes: the TOFU-pinned or Externally verified state itself, the recorded set of authorized origins for the publisher profile, and any pending migration-history events naming `P`. Cached manifests for those origins are explicitly orphaned and evicted by normal cache rules; the client MUST NOT use them as current after the deletion step. Closes the rc.14 ambiguity about what a `K_publisher.pub` abandonment removes from local storage.

**§10 Migration confirmation - `affirmative confirmation` defined (N14)** - The phrase "the user's affirmative confirmation" is now defined explicitly as the user activating a dedicated chrome control whose semantics are unambiguously "accept the migration" - a button, key combination, or equivalent affordance. Passive events (focus changes, mouseover, scroll, dismissal of unrelated UI, navigation away and back, timeout-based auto-acceptance) are explicitly excluded from counting as affirmation.

**§10 Migration confirmation - `trust-state lifetime` defined (N15)** - The phrase "during the same trust-state lifetime" used in the migration re-prompting allowance is now defined: a trust-state lifetime for a publisher identity `P` begins when the client transitions `P` into a retained trust state (TOFU pinning or Externally verified) and ends on (a) user-invoked abandonment, (b) revert to First contact through Changed/mismatch resolution, or (c) user-initiated identity reset. No implicit expiration timer. Re-prompting on the same `(announcing_origin, successor_origin)` pair is now also required when the recall check defined in "Cross-session migration history" names the successor as a previously-replaced address.

**§10 Chain depth and cycle prevention - current origin after cycle rejection (N21)** - When a successor address is rejected as a chain cycle under the `visited_origins` rule, the spec now states explicitly that the publisher profile retains the most recently verified successor adopted earlier in the same flow as the current origin, and that the flow's root origin remains accessible through publisher-history controls. Future fetches addressed at any origin in `visited_origins` MAY use that origin's cached manifest if one is held and is still within its refresh policy; the cycle rejection invalidates the new migration adoption, not the prior verifications.

**§11 `E_ORIGIN_EXPIRED.details.now` - minute-precision rounding (N18)** - The `details.now` field SHOULD be rounded down to minute precision (UTC, RFC 3339 form `YYYY-MM-DDTHH:MM:00Z`). The minute-precision constraint limits the precision of any clock-skew leak when the diagnostic is logged or transmitted to third parties (crash reports, support channels) without compromising the diagnostic's usefulness for clock-skew troubleshooting, where minute-level resolution is sufficient.

**Lotto 8 - second errata tranche (N33-N36)**

A fourth-pass audit pass surfaced four additional low-severity textual issues. They are aggregated into a single follow-up commit on top of Lotto 7. All four are clarifications or consolidations of rules already implied by adjacent text; none alters wire format, schema, diagnostic catalog, or any existing MUST-level requirement.

**§10 and §11 `origin.not_after` boundary wording (N33)** - Three spots described the `origin.not_after` boundary check in inclusive terms inconsistent with the strict normative formula. The §10 Stage 9 pipeline-summary item previously read "reject if the client's clock (within clock-skew tolerance) is at or after the declared instant", the §10 Stage 9 detail prose previously read "a manifest whose declared `not_after` is at or before the client's clock ... is rejected as `E_ORIGIN_EXPIRED`", and the §11 `E_ORIGIN_EXPIRED` catalog row previously read "the client's clock (within clock-skew tolerance) is at or after the declared instant". All three wordings contradicted the §06 phrasing ("strictly later than the declared instant") and the §10 past-bound tolerance formula `current_time > timestamp + 300 seconds` (strict, not inclusive). All three spots are now aligned to strict `>`: the pipeline-summary item cites "strictly later than the declared instant, per the past-bound tolerance formula in 'Clock skew tolerance' below"; the Stage 9 detail prose cites "strictly earlier than the client's clock ... the rejection formula is `current_time > not_after + 300 seconds`, strict"; the §11 catalog row cites "the client's clock is strictly later than the declared instant, applying the past-bound clock-skew tolerance (`current_time > not_after + 300 seconds`)". Textual alignment only. The normative comparison has always been strict `>` (defined at §06 since rc.14 and reinforced by the rc.15 past-bound tolerance formula); only the prose and pseudocode wording in §10 and §11 were inconsistent.

**§05 Small-order `R` not rejected (N34)** - The Ed25519 strict profile in §05 rejects small-order public keys (`A`) but does not reject signatures whose `R` component is a small-order point on the Ed25519 curve, consistent with the `verify_strict` mode of `ed25519-dalek` referenced as the canonical implementation. The §05 "Signature (`R || S`) validation" subsection previously specified only the canonical-encoding check on `R` and was silent on small-order treatment. A clarifying paragraph is added at the end of the subsection, stating explicitly that small-order rejection applies only to `A` and not to `R`, and that a signature with small-order `R` is accepted if it passes canonical encoding, `S < L`, and the cofactorless verification equation `[S]B = R + [k]A`. Textual clarification of existing behavior; no implementation change.

**§07 State update failure taxonomy (N35)** - The §07 "Consent model" subsection previously stated, in adjacent paragraphs, that an undeclared `(namespace, key)` combination causes the transaction document to be rejected, and that "rejecting a state update does not reject the transaction document". The two clauses cover different failure modes (schema/policy hard-fail on the document vs consent/storage soft-fail on the operation only), but the distinction was implicit. The "Consent model" wording is extended with an explicit failure taxonomy enumerating four cases: schema failure and policy failure reject the entire transaction document at Stage 5; consent failure and storage failure reject only the individual state operation, leaving the transaction document valid and renderable. Consolidates rules already present in §02, §07, and §10; no new requirement is introduced.

**§10 Publisher-supplied labels in chrome (N36)** - The §10 chrome rules previously placed the prohibition on publisher-controlled content in chrome ("Chrome separation") adjacent to per-field permissions allowing specific publisher-supplied fields (`manifest.navigation.label`, `meta.title`) to appear in chrome regions, but no single subsection enumerated the permitted fields or imposed display constraints on them as a class. A new subsection "Publisher-supplied labels in chrome" is inserted before "Chrome separation". It enumerates the two publisher-supplied label fields permitted in chrome and imposes three MUST-level requirements on them: display only after Stage 9 verification (already implied by the validation pipeline); visual distinguishability from client-asserted status (consolidating the existing rule that publisher content MUST NOT impersonate client-controlled status); opacity to in-band markup, terminal control sequences (ANSI, VT, OSC, CSI), and other escape mechanisms (extending to chrome the rendering-path opacity already required for state values in §07). Other publisher-supplied fields displayed in chrome (`state.purpose`, proposed state values, `canary.statement`, `canary.freshness_proof`) are governed by safe-display rules in their owning sections, which are referenced from the new subsection. Consolidates existing rules; no new permission to display additional fields in chrome is granted.

**Lotto 9 - third errata tranche (N37-N40)**

A fifth-pass audit pass surfaced four additional issues: a normative restructuring of the §10 migration successor adoption flow, a versioning-rule contradiction between §11 and the release engineering convention, and two v1.0 limitations that were implicit in the spec but not surfaced in §00. They are aggregated into a single follow-up commit on top of Lotto 8.

**§10 Migration successor adoption - verified pending state introduced (N37)** - The §10 "Successor verification" subsection previously stated, in adjacent paragraphs, that the client "adopts the successor origin into the publisher profile" upon successful verification, and that for TOFU pinned and Externally verified trust states the client MUST obtain affirmative user confirmation "before navigating to the successor origin and before migrating any cached state to it". The wording conflated two distinct states - verified but not yet user-confirmed, and adopted as an authorized origin of the publisher profile - and left the publisher-profile transition implicitly happening at verification while the related behaviors were gated on confirmation. The subsection is restructured to introduce a **verified pending successor** state explicitly. Post-verification, the successor is recorded as verified pending in the publisher profile, and the cached successor manifest is current for the successor origin under the standard caching rules (preserving the existing direct-navigation behavior); the successor is not yet an authorized origin of the publisher profile, and the client MUST NOT auto-navigate to it from the announcing origin's session, migrate cached state to it, or render publisher-controlled content from it under that session. Adoption - transition to authorized origin status and recording of the Adoption event in publisher history (rc.18 N30) - occurs at the affirmative user-confirmation step defined in the following subsection, retaining the existing trust-state-dependent strength (MUST for TOFU pinned / Externally verified; SHOULD for First contact, with an explicit relaxation that a client omitting the First contact dialog MAY treat verification as adoption provided the chrome migration notice is displayed). The §10 "Anti-downgrade and anti-forgery interaction" wording at "adopt only on success" is updated to "adopt only on user-confirmation success" for consistency. No new wire format; no new schema; no new diagnostic code; the rc.18 Adoption event mechanism in publisher history is unchanged because Adoption events are recorded at user confirmation, which matches the pre-restructuring intent. An rc.17 implementation that correctly gated auto-navigation, state migration, and content rendering on confirmation per §10:385 already implements the new staging; the restructuring makes the staging explicit and removes the ambiguity around the meaning of "adopts into publisher profile" pre-confirmation.

**§11 Versioning - RC-cycle additive relaxation made explicit (N38)** - §11 "Protocol version" previously stated that "any change to the accepted wire format, including additive fields, is a breaking change at the protocol level. There is no middle ground for additive minor revisions within v1." Read literally, this contradicted the README release-engineering rule (clarified in rc.17) that allows additive optional fields during the pre-release rc cycle without bumping `spec_version`, under which `migration_pointer` (rc.13) and `origin.not_after` (rc.14) were introduced. The two statements are reconciled by adding a paragraph to §11 that distinguishes the wire-format stability guarantee that holds from v1.0 final onward (the no-additive-changes rule) from the pre-freeze rc-cycle relaxation (documented in `docs/RELEASES.md` and explicitly not part of the v1.0 conformance profile). Conformance is judged against v1.0 final; rc intermediate states are not separately conformant artifacts. No normative behavior change; resolves an inconsistency between §11 and the release engineering convention.

**§00 Limitation - content rollback by an authorized runtime key (N39)** - The v1.0 limitations list in §00 did not explicitly enumerate the absence of in-document rollback detection: a server in possession of a previously-issued signed content document for a given `path` can serve that older instance even after the publisher has published a newer instance for the same path, and a client has no protocol-level basis to distinguish stale from current within the same `K_runtime` authorization window. The limitation is implied by the absence of a `revision`/`content_hash` field and is acknowledged as a v2 candidate in `docs/design-decisions.md`, but was not surfaced in §00. A new limitation entry "No detection of content rollback by an authorized runtime key" is added to the §00 list, stating the gap, naming the operator mitigations (rotation of `K_runtime`, publication of a new manifest with a later `canary.issued_at`, out-of-band republication of sensitive updates), and pointing to the v2 candidate.

**§00 Limitation - remembered consent does not reprompt on policy widening within scope (N40)** - Remembered consent under §07 is keyed on `(K_publisher.pub, namespace, key, mode)` and does not include `purpose`, `max_size`, or `max_lifetime`. A publisher can therefore widen the policy for an existing `(namespace, key, mode)` combination (longer `max_lifetime`, larger `max_size`, changed `purpose`) and have subsequent set operations committed under the remembered consent without reprompting the user, provided each new operation stays within the new policy bounds. Existing stored entries retain their commit-time bounds per §07 "Client behavior on policy changes"; the relaxation applies only to new operations after the policy change. The behavior is the spec's intent - tighter binding would be a v1.1+ tightening - but was not surfaced as an explicit limitation in §00. A new limitation entry "Remembered consent does not reprompt on policy widening within the same `(namespace, key, mode)` scope" is added, naming the keying tuple, the relaxation, and the future-tightening candidate status.

**§10 Migration withdrawal - verified-pending case (N41, follow-up to N37)** - N37 introduced the verified-pending successor state, but the §10 "Anti-downgrade and anti-forgery interaction" subsection at line 404 covered only what happens to an *adopted* successor when the announcing manifest is replaced by a newer manifest that omits `migration_pointer`. The case of a verified-pending successor at the time of withdrawal was not explicitly addressed by either the pre-N37 wording or the N37 restructuring. A clarifying sentence is added to the §10:404 paragraph: a verified pending successor that has not yet been adopted is purged from the publisher profile on withdrawal; the cached successor manifest may remain in the manifest cache under the standard caching rules but is no longer associated with a pending migration from the announcing origin, and the verified-pending-state behaviors defined under "Successor verification" no longer apply. Documents the natural semantics; an rc.17 implementation had no verified-pending concept and so could not have implemented this case incorrectly.

**Lotto 10 - fourth errata tranche (N42-N44)**

A sixth-pass audit (external Soatok-style cryptographic review) surfaced three additional issues with normative impact. They are aggregated into a single follow-up commit on top of Lotto 9 / N41. Unlike Lotto 7-9 which were predominantly clarifications and consolidations, Lotto 10 contains two normative tightenings (a value-range narrowing on the canary interval and a SHOULD->MUST elevation on First-contact migration confirmation) and one additive normative section on submit validation timing. All three are bounded in scope; wire format, schema, and the diagnostic catalog remain unchanged.

**§08 Canary interval ceiling - 90 days -> 30 days (N42)** - The canary interval `next_expected - issued_at` previously permitted up to 90 days, with the operator playbook discouraging 60-90 days as "the canary stops being a meaningful security signal" and identifying 30 days as the upper end of the medium-threat band. The §08:81 MUST ceiling is now tightened from 90 days (7776000 seconds) to 30 days (2592000 seconds), aligning the protocol-level MUST with the operational upper bound previously recommended by the playbook. The 7-day MUST floor is unchanged. The §08:88 prose is rewritten: higher-threat publishers SHOULD choose intervals close to 7 days; lower-threat publishers MAY choose intervals up to the 30-day ceiling. The operator playbook §7 "Choosing canary interval" is restructured: the "Low-threat - 30 to 60 days" and "Discouraged - 60 to 90 days" buckets are removed; the remaining buckets are "High-threat - 7 days" and "Standard - 14 to 30 days". References to the 90-day cap in operator-playbook §3.3 and §16 "The compromise window" are updated to 30 days. The §08:154 Invalid state description ("7-to-90-day bounds") is updated to "7-to-30-day bounds". The change is a normative tightening: an rc.17 publisher emitting a canary interval in `(30, 90]` days is non-conformant under rc.18. The operator playbook already discouraged the 60-90 days portion of this range; the 31-60 days portion is the genuinely new restriction. Wire format and schema are unchanged; only the accepted value range narrows.

**§10 First contact migration confirmation - SHOULD -> MUST (N43)** - The §10:390 user-confirmation requirement for migration adoption at First contact was previously SHOULD-level, with rationale that "the migration-confirmation dialog is informational rather than a continuity-preservation step". An external audit observed that this permits silent auto-adoption of a successor at First contact, opening a vector under temporary `K_publisher` compromise (a compromise window can publish a migration announcement that is then auto-adopted by every First-contact client without prompting) and a cross-session ping-pong vector where the same First-contact identity re-traverses an `A -> B -> A -> B` chain on each fresh navigation without user awareness. The §10:390 SHOULD is tightened to MUST under the same definition of "affirmative confirmation" as for Externally verified and TOFU pinned states. Cascading updates: the §10:383 "SHOULD-level relaxation of that subsection permits a client that omits the confirmation dialog to treat verification as adoption" sentence (introduced by Lotto 9 / N37) is removed; the user-confirmation step is now MUST for all announcing trust states (Externally verified, TOFU pinned, First contact), and a verified pending successor never transitions to adopted without it. The §10:429 "For First-contact identities, where one automatic migration hop is permitted without a user-confirmation prompt under 'User confirmation' above, this re-traversal can be silent" wording is updated: the prompt is now always present, and the residual cross-session concern shifts from "silent re-traversal" to "uninformative re-traversal prompt" (the per-flow `visited_origins` does not surface the cycle without cross-session history; the cross-session history mitigation remains SHOULD per Limitation #3). The §10:443 recall-window text is updated since First contact already requires confirmation; the recall-information surfacing requirement remains SHOULD. The change is a normative tightening: an rc.17 implementation that auto-adopted a migration successor at First contact without prompting is non-conformant under rc.18. The cost is one additional prompt on First-contact navigations that encounter a `migration_pointer`; the benefit is closure of the silent-adoption vector.

**§09 Submit validation timing - server-side side-channel guidance (N44)** - The §09 transport section previously had no normative guidance on submit validation timing. The natural sequential publisher-side validation path (JSON parse, JCS canonicalization, schema check, `request_state` policy check, `request_hash` computation) exposes the rejecting stage as a server-side timing signal that an attacker probing with crafted submit bodies can sample without authentication. The §00:170 Limitation #12 acknowledges the analogous *client-side* concern (validation pipeline diagnostic-stage emission) but the *server-side* mirror was unaddressed. A new §09 subsection "Submit validation timing" is inserted between "Submit body size limit" and "Image resource fetches". Publishers SHOULD adopt one of two disciplines: complete-validation (run all stages regardless of earlier failures, accumulating any rejection reason for the final response without short-circuiting), or randomized-delay (50-200 ms uniformly distributed per request before responding, independent of validation outcome). The rule is SHOULD-level because the protocol cannot enforce timing properties on remote endpoints; operators of high-threat deployments are expected to verify their stack against the discipline. The client-side concern remains acknowledged as Limitation #12 and is not addressed by this rule. Additive normative section; no impact on client conformance and no wire-format change. An rc.17 publisher implementation is not retroactively non-conformant because the rule is SHOULD-level guidance newly added; rc.18+ publishers operating in high-threat deployments are expected to align.

**Diagnostic catalog summary.** No new error codes. One existing `details` field gains a precision constraint: `E_ORIGIN_EXPIRED.details.now` rounds down to minute precision. The rc.16 `details` schema is described as `SHOULD include`, so the precision constraint does not break any conforming rc.16 implementation that already emits second-precision values; it tightens future implementations.

**Wire format summary.** Unchanged. The wire-level `spec_version` remains `"1.0"`. No schema additions or removals on any document kind. JCS canonicalization, NFC, byte caps, and all other input restrictions are unchanged. All rc.17 documents validate identically under rc.18.

**Behavioral compatibility.** Lotto 7-9 changes are clarifications, additive extensions, or definitional tightenings of existing rules. The `Replacement` event extension (N30) changes the set of recorded events under the SHOULD-level migration-history mechanism but does not change any MUST-level requirement; rc.16 implementations that do not maintain migration history at all remain fully conformant. ### v1.0-rc.14

Date: 2026-05-10

Changes since v1.0-rc.13:

This rc lands the audit-driven hardening tranche identified as Lotto 3, split into two batches: tightening of `MAY`/`SHOULD` to `MUST` and clarification of underspecified resolution flows (Lotto 1, patch-level, no schema change), and additive features for origin lifetime declaration and migration chain control (Lotto 2, additive, schema and diagnostic-catalog changes).

**Lotto 1 - patch-level tightening (§02, §03, §08, §09, §10)**

- §02 Closed-schema eager-validation MUST (W16) - New normative sentence. Implementations MUST eagerly validate every top-level field of a document against the closed schema. A parser that examines only the fields it intends to use, and ignores or defers fields it does not recognize or does not currently consume, is non-conformant: schema validation is a whole-document check at Stage 5, regardless of which fields a particular execution path reads.
- §03 No retry on image verification failure (W28) - New normative subsection. After a failure at any of steps 2-9 of the image verification pipeline (transport failure, Content-Type or media-type mismatch, oversize, hash mismatch, decode failure, dimension mismatch, pixel-budget violation), the client MUST NOT re-fetch the same `src` for the same `image` block within the same document rendering session. The bound triple `(src, sha256, media_type)` is declared by the signed document; refetching cannot change the signed expectation. A user-initiated reload, or a document fetched anew under a refreshed manifest, is a new rendering session and is not blocked.
- §08 `freshness_proof` summary visibility (N4) - Strengthened the existing presence/absence signaling rule. The presence-or-absence signal MUST be visible in the canary's summary surface - the surface that exposes the canary state without requiring expansion of a detail view, drawer, or other collapsed UI. A client that hides the presence signal exclusively behind a collapsed detail surface is non-conformant. The contents of `freshness_proof` itself, when present, MAY remain in the expandable detail surface; only the presence-or-absence indicator is required in the summary.
- §08 Canary-conflict resolution control (N2) - Strengthened the existing canary-conflict warning rules. The client MUST present an explicit user-accessible resolution control as part of the chrome warning, offering at least two distinct actions: "Keep the retained identity" (acknowledges the conflict, clears the always-visible warning, records the event in publisher history) and "Abandon the retained publisher identity" (defined in §10). Passive events MUST NOT clear the warning. The prior text required offering "the option to abandon" but did not prescribe that the offer take the form of a user-accessible UI control; clients that surfaced the warning without a usable resolution affordance left the user in a permanently bloccato state.
- §09 No `Range`/`If-Range` request headers; no `206 Partial Content` (W26) - Added `Range` and `If-Range` to the prohibited request-header list for both `GET` and `POST` requests, with a normative paragraph explaining the rationale (an Entangled document is signed as a whole and is verified, hashed for the byte cap, and digested for image binding against its complete byte sequence; partial-content fetches deliver bytes that do not correspond to any signed object). Publishers MUST treat any request carrying `Range`/`If-Range` as malformed; publishers MUST NOT emit `206 Partial Content`. The general "unlisted `2xx`" rule already covered `206` on the client side, but the previous text did not name it explicitly and did not forbid the client from issuing `Range` requests.
- §10 Abandoning a retained publisher identity (N1) - New normative subsection specifying the semantics of the "abandon retained publisher identity" action offered by the canary-conflict resolution control (§08), the Changed/mismatch resolution flow, and any equivalent high-threat-mode UI. The action MUST: delete the active trust-state record for `K_publisher.pub = P`; record the abandonment in publisher history as a terminal event including reason class; dissociate any authorized origins (including successor origins adopted under the publisher profile via `migration_pointer`); and refuse to use retained `K_runtime` authorization-history entries for verifying any new content fetched after the abandonment as if it were current publication. After abandonment, a subsequent navigation to any origin presenting `publisher_pubkey == P` is treated as First contact; the client MUST surface that an abandonment record exists at the First-contact prompt. The new subsection also distinguishes "abandon the site" (Changed/mismatch resolution; preserves the retained identity record) from "abandon retained publisher identity" (severs the trust relationship); the two are distinct user actions and MUST be presented in chrome as distinct choices.
- §10 Migration confirmation for retained identities (N5) - Strengthened the prior `SHOULD` on user confirmation before automatic navigation to a successor origin. The strength now depends on the announcing publisher's trust state: for **Externally verified** or **TOFU pinned** identities, the client MUST obtain the user's affirmative confirmation before navigating to the successor origin and before migrating any cached state; for **First contact**, the prior `SHOULD` is retained. The confirmation dialog MUST present both addresses, the complete 24-word PIP, and the `migration_pointer.announced_at` timestamp, with no destructive default. A client that has obtained confirmation for a specific `(announcing, successor)` pair MAY proceed without re-prompting for the same pair within the same trust-state lifetime. Background auto-fetch of the successor manifest for verification purposes remains permitted, provided publisher-controlled content from the successor is not rendered before user confirmation.

**Lotto 2 - additive (§05, §06, §10, §11, §00, §01)**

- §06 `origin.not_after` (W1) - New OPTIONAL field on the manifest's `origin` object. Declares the UTC instant after which the publisher commits that this carrier endpoint is no longer authoritative for the site under `K_publisher`. Encoded in the same RFC 3339 UTC form as `updated` (`YYYY-MM-DDTHH:MM:SSZ`). Constraints: MUST be strictly later than `canary.issued_at`; SHOULD be strictly later than `canary.next_expected`; MUST NOT be more than 5 years after `canary.issued_at`. A manifest with `origin.not_after` violating these constraints is rejected at Stage 5 as `E_ORIGIN_INVALID`. A manifest whose `origin.not_after` is at or before the client's clock (within the §10 clock-skew tolerance) is rejected at Stage 9 as `E_ORIGIN_EXPIRED`; anti-downgrade still applies, and a newer manifest for the same `K_publisher.pub` supersedes the expired one. Absent in the manifest when no expiration is declared (per §04 no-`null` discipline). Bounds the time window during which an attacker holding a compromised `K_origin_priv` can serve cached clients of an abandoned origin.
- §05 `K_origin` compromise summary - Extended the recovery paragraph to acknowledge `origin.not_after` as the optional mechanism that bounds the post-compromise serving window for cached clients; recovery remains in-band only insofar as the cached client observes the new manifest or its `migration_pointer` before `not_after` is reached.
- §10 Origin migration chain depth and cycle prevention (N6) - New normative subsection. A client supporting publisher profiles MUST enforce both an automatic chain-depth limit (at most one `migration_pointer` hop adopted without re-prompting under "User confirmation"; further hops require a new confirmation, evaluated under the trust state of the publisher identity at the intermediate origin) and a per-flow visited-origin set (`visited_origins`, initialized with the announcing origin; a successor address already in `visited_origins` is rejected as `E_MIGRATION_INVALID` with `details.reason = "chain_cycle"`). The `visited_origins` set is per-navigation and per-publisher-profile, reset when the migration-resolution flow ends, and not persisted across sessions. The chain-depth limit applies to automatic hops only; user-confirmed hops reset the counter. High-threat mode MAY set the automatic limit to zero. When the limit is reached without user confirmation, the deeper successor is treated as "pending user action": chrome displays the announcement, but the client MUST NOT auto-navigate, fetch publisher-controlled content from the deeper successor, or migrate cached state to it.
- §10 Stage 9 - Updated the Stage 9 pipeline-summary listing to include the `origin.not_after` check and the `migration_pointer` successor/chain-depth check. ### v1.0-rc.13

Date: 2026-05-10

Changes since v1.0-rc.12:

This rc lands the audit-driven hardening tranche split into two batches: tightening of `MAY`/`SHOULD` to `MUST` in §10 and §08 (Lotto 1, patch-level, no schema change), and additive features in §06, §08, §04, and the corpus (Lotto 2, additive, schema and diagnostic-catalog changes).

**Lotto 1 - patch-level tightening (§10, §08, §01)**

- §10 First contact -> TOFU pinned (W18) - Strengthened to `MUST` an explicit affirmative pinning prompt. Successful manifest verification, content rendering, dismissal of the first-contact notice, navigation away, or any other passive event MUST NOT cause the transition. The client MAY render the first-contact content before presenting the prompt; rendering does not constitute pinning. The prior `SHOULD` form, which permitted "first successful render" to trigger the transition, is removed: a client that pins on first render is now non-conformant.
- §10 PIP display requirements (W11/W12) - New normative subsection. The client MUST display the complete 24-word PIP at First contact, during Changed/mismatch resolution, in expandable detail surfaces, and anywhere the user is being asked to compare publisher identity against an out-of-band reference. Truncated, prefix-only, suffix-only, or "first-N + last-M" displays are not conformant. A 24-word BIP-39 PIP encodes the full 256-bit `K_publisher.pub` plus an 8-bit checksum; partial display reduces attacker grinding cost.
- §10 Multiple origins per publisher (W23) - `publisher_profile` strengthened to `MUST` for clients that retain trust state across sessions. A cross-session client without publisher-profile records is not conformant. Stateless clients are exempt and MUST present their statelessness in chrome.
- §10 Render dependence on manifest verification - New consolidated `MUST` (formerly distributed across §05, §06, §10): no document, block, or referenced resource is rendered until manifest signature, trust-state, canary, and origin-binding stages have completed. Chrome elements (origin, loading indicator, transport errors, verification progress) are exempt; the rule covers publisher-controlled content.
- §10 Conditional always-visible warnings - Added canary conflict warning entry to the chrome warnings list; persists until the user resolves it.
- §08 Equal `issued_at` conflict (W7) - Reframed `E_CANARY_CONFLICT` as a fault condition on the publisher identity, not a recoverable transient error. The client MUST NOT pick a deterministic "winner" between conflicting manifests by lexicographic comparison, payload size, `runtime_pubkey` value, or any other tiebreaker over manifest content; a deterministic tiebreaker is gameable by an attacker holding `K_publisher_priv` and would mask the underlying fault. The retained pre-conflict manifest stays in place for current rendering and anti-downgrade; the conflict is surfaced as a prominent chrome warning analogous to Changed/mismatch, with an option to abandon the retained publisher identity. The warning persists until the user explicitly resolves it.
- §01 - Publisher profile glossary entry now notes the conditional `MUST` for stateful clients.

**Lotto 2 - additive (§06, §10, §11, §04, §08, §02, §00, §01, corpus)**

- §06 `migration_pointer` (W22) - New optional top-level manifest field. The publisher's signed announcement of a successor carrier endpoint operated under the same `K_publisher`. Absent when no migration is announced; per §04 no-`null` discipline, encoded by omitting the field rather than by a `null` value.
- §10 Origin migration handling - New subsection. On match, the successor origin is adopted into the publisher profile. On mismatch, the announcement is rejected as `E_MIGRATION_MISMATCH`. - §11 - Added `E_MIGRATION_MISMATCH` and `E_MIGRATION_INVALID` to the Binding diagnostics (Stage 9) catalog. `E_MIGRATION_MISMATCH` SHOULD include in `details` the announced successor address, the successor and announcing publisher keys, and the specific mismatch field. `E_MIGRATION_INVALID` covers structural well-formed but semantically invalid announcements (successor equals announcing, `announced_at` after `updated`, carrier mismatch).

### v1.0-rc.7

Date: 2026-05-08

Changes since v1.0-rc.6:

- §00 - Added a "v1.0 limitations" subsection that consolidates protocol-level limitations a v1.0 implementation should disclose to users: no in-band runtime-key revocation, canary expiration is not cryptographic revocation, no general anti-replay against malicious backends, no historical-content bootstrap for new clients, no in-band origin-migration discovery, no protection from a malicious publisher, image decoding is a residual attack surface. Each bullet references the section that defines the underlying rule.
- §03 - Added a "Decoder safety" subsection. Hash verification authenticates image bytes against the signed document but does not make decoding safe; a publisher with a valid `K_runtime` may sign a document referencing an intentionally crafted image. Implementations SHOULD use memory-safe decoders, hardened parsers, sandboxed processes, or other isolation appropriate to the deployment environment. Protocol-level rejections (media-type allowlist, no SVG, no animation, hash verification, dimension limits, pixel budget) are necessary but not sufficient.
- §07 - Strengthened the request-state consent prompt: the client MUST explain that the item is included in future submit requests across every submit endpoint under the publisher's identity, not only the current form or endpoint. Made explicit that request-state scope in v1 is publisher-wide and endpoint-scoped request state is not part of v1.
- §10 - Strengthened the First contact -> TOFU pinned transition from MAY to SHOULD. The recommended trigger is the user explicitly choosing to continue to the site or the first successful render of content. The client SHOULD document, in user-accessible form, the trigger it uses. Other triggers (e.g. dismissal of the first-contact notice) remain permitted.
- §10 - Added a clock-skew UX hint. When rejecting a timestamp because it exceeds the 300-second tolerance, the client SHOULD indicate to the user that the local clock may be incorrect, since clock skew is a likely cause of false positives. The protocol-level diagnostic remains the one specified for the failing field; the advisory is a presentation hint, not a separate diagnostic code.

This rc is editorial. It does not change the wire format, signature inputs, signature input construction, or the diagnostic code catalog.

### v1.0-rc.6

Date: 2026-05-08

Changes since v1.0-rc.5:

- §02 - Reserved `/manifest.json` at the protocol level. The path is now explicitly forbidden as a content document `path`, transaction `in_response_to`, image `src` (§03), submit endpoint, and inline-link target. Added a bullet to each path-syntax restatement.
- §02 - Clarified the scope of the `request_id` / `request_hash` binding: they bind the signed transaction response to the submit body the client sent, but are not a general anti-replay mechanism against a malicious or compromised publisher backend, which may still receive, store, or reuse submit bodies and sign transaction responses for any submit body it accepts.
- §03 - Replaced the abstract image-resource verification list with a precise, ten-step ordered sequence that names the specific diagnostic for each step (`W_IMAGE_FETCH_FAILED`, `W_IMAGE_CONTENT_TYPE`, `W_IMAGE_OVERSIZE`, `W_IMAGE_HASH_MISMATCH`, `W_IMAGE_DECODE_FAILED`, `W_IMAGE_DIMENSIONS`, `W_IMAGE_BUDGET`). Made explicit that the declared `media_type` is authoritative for decoder selection while the response `Content-Type` is checked separately for header consistency.
- §03 - Added a normative WebP animation detection requirement. A client MUST determine animation status before rendering, by inspecting the RIFF chunk structure or by querying its decoding library. An implementation whose WebP library cannot expose this property reliably MUST reject all WebP resources or disable WebP support. Silently rendering only the first frame of an animated WebP is non-conformant.
- §08 - Refined the equal-`issued_at`-not-a-conflict criterion to depend solely on the JCS-canonical signed payload rather than on byte-for-byte wire equivalence and signature equality. Under deterministic Ed25519 (RFC 8032) signing the same payload under the same key produces an identical `sig`, so the canonical-payload criterion subsumes the signature criterion; framing it as canonical payload makes the protocol-level invariant clear.
- §10 - Added a "Verification key trial order" section for historical content. The order in which retained `K_runtime.pub` entries are tried is implementation-defined (reverse chronological by first-observed `issued_at` recommended). Verification under more than one distinct retained key for the same document is treated as a cryptographic anomaly, an implementation bug, or authorization-history corruption; the client MUST reject the document. No new normative error code; clients SHOULD log the condition.

This rc clarifies path reservation, image verification ordering, and historical-content trial order, and scopes the submit-binding guarantees against backend replay. None of these changes alter the wire format, signature inputs, signature input construction, or the diagnostic code catalog.

The wire-level `spec_version` remains `"1.0"`.

### v1.0-rc.5

Date: 2026-05-08

Changes since v1.0-rc.4:

- §04 - Added an explicit ABNF integer grammar (`integer = "0" / non-zero-digit *digit`) and a parser-level enforcement rule. Numeric tokens MUST be validated lexically before any conversion to a numeric type. JSON parsers that convert numeric tokens to IEEE 754 binary64 first are non-conforming for Entangled use because they cannot reliably distinguish `42` from `42.0` or `1e0`, lose precision above `2^53` (so `9007199254740993` becomes `9007199254740992`), and conflate `-0` with `+0`. Implementations MUST use a parser that either exposes raw numeric tokens for lexical inspection, or rejects non-integer tokens at parse time, or perform a separate raw-bytes validation pass. The integer's decimal value MUST be in `[0, 2^63 - 1]`.
- §04 - Added a "Strict base64url decoding" section that pins decoder behavior for every base64url-encoded field in the protocol (`sig`, `publisher_pubkey`, `origin_pubkey`, `runtime_pubkey`, `expected_publisher_pubkey`, `request_id`, `image.sha256`, `transaction.request_hash`). The decoder MUST use only the URL-safe alphabet (`A-Z`, `a-z`, `0-9`, `-`, `_`), reject every character outside it including `+`, `/`, whitespace, line breaks, and non-ASCII characters, reject the padding character `=`, enforce the field-declared exact ASCII length, and reject non-canonical trailing-group encodings (the unused bits in the final encoded character MUST be zero). Permissive decoders that accept padded input, ignore whitespace, accept the standard `+`/`/` alphabet, or accept non-canonical trailing-group encodings are non-conforming.

This rc tightens parsing strictness without changing the wire format, signature inputs, signature input construction, or the diagnostic code catalog. Documents that an rc.4 client accepted by virtue of a permissive JSON parser or base64 decoder may be rejected by an rc.5 client; conforming current parsers and decoders are unaffected.

The wire-level `spec_version` remains `"1.0"`.

### v1.0-rc.4

Date: 2026-05-08

Changes since v1.0-rc.3:

- §02 - Clarified that `request_hash` is computed over the JCS-canonical bytes of the parsed submit body, not over the wire bytes received. The formula already pinned this; the prose previously read "the exact submit body bytes received, after JCS-canonicalization", which was ambiguous. Insignificant whitespace and member ordering in the wire submit body are now stated explicitly to not affect the hash.
- §05 - Added an "Ed25519 verification profile" section that pins the strict, cofactorless validation rules. Public keys MUST be in canonical encoding and MUST NOT be small-order; signatures MUST use canonical `R` and canonical `S` (`0 <= S < L`); verification uses the cofactorless equation `[S]B = R + [k]A`. The profile aligns with `verify_strict` in `ed25519-dalek`. Implementations MUST NOT use cofactored verification or accept non-canonical encodings. This eliminates cross-implementation divergence in signature acceptance, in particular between libraries that historically split between RFC 8032 permissive and ZIP-215-style strict modes.
- §07 - Replaced the "opaque byte strings" terminology for state values with "opaque UTF-8 strings", aligning the safe-display subsection with the value field schema (`value` is a UTF-8 string). Editorial only; no wire-format change.
- §09 - Added a "Content-Encoding and Transfer-Encoding" section that forbids both headers in both directions. Publishers MUST NOT use `Content-Encoding` on any Entangled response or `Transfer-Encoding` (including `chunked`) on any response; clients MUST disable automatic HTTP-layer decompression and reject responses carrying either header. The same rules apply to submit `POST` request bodies. Closes the interop ambiguity that arose when transport stacks decompressed responses by default, which would change the byte sequence used for the byte cap (§02, §06, §10), for `Content-Length` consistency checks, and for the SHA-256 digest of image resources (§03). Adds a normative implementation note that conforming clients must use an HTTP stack whose default header injection and decompression can be disabled.
- §11 - Added `E_TRANSPORT_CONTENT_ENCODING` and `E_TRANSPORT_TRANSFER_ENCODING` to the Stage 1 transport diagnostics catalog.

This rc tightens transport and signature-verification behavior. Responses or signatures that an rc.3 client might have accepted under HTTP-stack default decompression or under cofactored Ed25519 verification can now be rejected; conforming current signers and HTTP stacks are unaffected. The wire-level `spec_version` remains `"1.0"`; the rc number tracks pre-release stabilization, not protocol identity (§11).
